## 二、三个「原来记成缺机器」的缺口 → 替代方案

### 2.1 第三方可复现构建(M7 验收)

原判据:第三方用同一命令编出**逐字节相同**的二进制。三层替代,由弱到强:

| 层 | 做法 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| **R1 异路径变体** | 在 `E:\rb\ouuut-browser` 从 `git archive` 全新落地,删掉一切缓存(NuGet / depot_tools cache / `out/`),按 `tools/` 文档从零走完 | 路径无关、盘符无关、脚本幂等、缓存不是必需 | 不是另一台机器 |
| **R2 干净 VM** | Hyper-V 建 Win11 评估版 VM(全新 OS,**没有 VS/SDK**),在 VM 里只照文档 bootstrap + 全量构建 | 一台**没有任何前置状态**的 Windows 上,文档足以从零走完并得到同一字节 —— 本机能做到的最强证据 | **不是第三方,也不是另一台物理机**;仍需一次管理员权限(R2 未做 = M7 那条保持未完成) |
| **R3 公开后第三方** | 仓库转 public 后,由外部照文档跑一次,结果贴进 `docs/里程碑.md` | 真正的第三方复现 | 需时间,不可控,**不阻塞发布** |

**判定**:R1 立即做(约 **4 小时机时**,无人值守);R2 在发布前做(**一天机时**);R3 长期兜底。

### 2.2 真服务器上跑三种档案(M5 验收)

替代 = **vps-jp**。前置是 P1 的 POSIX 通道分支,**那一步 2026-10-25 已完成**(见 §三 P1),
所以这条缺口的下一步只是「在 Linux 上把三种档案各起一次」(P2)。

技术依据(已在本机源码树核对,不是推测):上游 POSIX 侧硬编码 **fd 3 读 / fd 4 写** ——
`chromium/src/content/browser/devtools/devtools_agent_host_impl.cc:269-270` 取 `kReadFD` / `kWriteFD`,
且 `#if BUILDFLAG(IS_WIN)` 那段走的才是 `--remote-debugging-io-pipes` 命名管道(补丁 0004 改的就是它)。
Node 侧接法也是走通的旧路:`stdio: ['ignore','pipe','pipe','pipe','pipe']`,第 3/4 号索引即浏览器要的 fd 3/4。

⚠️ **事后更正(2026-10-25,P1 做完之后)**:原先这里写「只需要把通道抽成接口 + 补一个 POSIX 实现」——
**不准确**。做完才发现 `native/binding/cdp-pipe.mjs` 里那条 fd3/4 的路**本来就在**(按平台默认选),
真正缺的是**错误处理**:写端 `child.stdio[3]` 没挂 `error`,对端一死抛的 `ECONNRESET` 成了未捕获异常。
所以这一包的真实工作量是「**一行缺失的处理 + 语义对齐**」,不是「新增一套传输」。见 §三 P1 与 `docs/坑与解法.md` 坑-31。

### 2.3 自动更新真链路(M7)

**这不是机器缺口,是归类错误** —— 在 vps-jp 上开一个只放静态文件的目录(`python3 -m http.server` 或 nginx)就是真服务端。
本文纠正归类。

### P1 · POSIX 通道分支 —— ✅ **已完成(2026-10-25)**

- **实际改动**(比原设想更小,不是「重写一套传输」):`native/binding/cdp-pipe.mjs` 里 **fd3/4 那条路本来就在**
  (`useNamedPipes` 默认按平台选)。真正的缺陷是**写端 `child.stdio[3]` 没挂 `error`** ——
  对端一死它抛 `ECONNRESET`,Node 直接抛成**未捕获异常**,报错还会窜到当时恰好在跑的用例上
  (一条根因伪装成两条无关失败)。修法:两端统一走 `noteTransportError`(**只记不拒**),
  诊断里带上传输层错误,`exit` 时若已报过错就不再等 2 秒兜底。见 `docs/坑与解法.md` **坑-31**。
- **验收结果**:
  | 平台 | 结果 |
  |---|---|
  | Windows | `306/306`,0 跳过(与改前一致) |
  | Linux(`vps-jp`) | **红恒为 0**(改前 `298 过 / 2 红`);`300 过 / 6 跳过`(dist 未就位)或 `304 过 / 2 跳过`(dist 就位) |
  | 真浏览器(Linux) | `Chrome/156.0.8078.47` → `createTab` → 快照 **397 字符**,含 `hello ouuut` / `pay now` / `[frame …]`(OOPIF) |
  | ADR-005 | `ss -ltnp` 连续 4 次采样 **零监听套接字** |
- **与原计划的一处偏离(照实记)**:原写「2 条平台门测试改为『各平台各测一份』」——**没做**。
  理由:Linux 上**通道片那 60 余条本来就跑在 fd3/4 上**(全仓只有 4 个测试文件 `import spawnCdpPipe`,
  合计 67 条,含 2 条 Windows 命名管道门与 4 条 dist 门;其余约 240 条是纯单测,与通道无关),
  分帧、超时、竞态、非法 JSON 都覆盖到了;再加一对对称用例只是重复覆盖。那 2 条 Windows 用例断言的是
  **命名管道特有行为**(管道名随机、不串台),在 POSIX 上没有对应物。6 条跳过 = 2 条平台门 + 4 条 `harness dist 未构建`。
- **顺带产出**:坑-31(POSIX 写端流错误)、坑-32(snap 私有 `/tmp` ⇒ `file://` 页面读不到,要放 `$HOME`)

### P2a · 把档案引擎接到会话通路 —— ✅ **已完成(2026-10-25,提交 `3cf19d6`)**

**为什么必须新开这一包**:P1 做完去跑「三种档案」时发现,`--profile-kind` **解析、校验、单测都在,就是没人消费它** ——
`git grep profileKind` 全仓只有 `launch-args.mjs`(+ 其测试)。`createOuUutRuntime()` 被调用时没传 `profiles`,
于是 `listProfiles()` 恒返回硬编码的单条 `{id:"default"}`,**`archive.mjs` 的三种 kind 与两层隔离从来没上过真链路**。
照原样「各起一次」只会得到三个一模一样的会话,什么都证明不了。

- **kind → 浏览器侧的映射**(依据:`archive.mjs` 头部 ADR-007 的 kind 表 + Chrome 自己的 browser context 语义):

  | kind | 浏览器侧 | 持久化 | 归属 |
  |---|---|---|---|
  | `real` | **默认 browser context**(**不给** `browserContextId`) | 由 `--user-data-dir` 决定 | 机器上恰好一个,且 `isDefault` |
  | `persona` | `Target.createBrowserContext { disposeOnDetach: false }` | 留在该 `--user-data-dir` 里 | 可创建;销毁需显式 |
  | `disposable` | `Target.createBrowserContext { disposeOnDetach: true }` | **不留痕**(detach 即销毁) | 关闭即销毁 |

  会话的档案集合 = `real`(给了档案目录时)+ 被选中的那个 kind(选的不是 real 且没给目录 ⇒ 用会话临时目录)。

- **接口(新模块 `native/binding/session-profiles.mjs`)**:
  `openSessionProfiles({ cdp, kind, userDataDir, profileId, name })` → `{ archive, profiles, sessionProfileId, dispose }`
  - `profiles` 即 `archive.listProfiles()` 的形状;`dispose()` 负责销毁 disposable 的 browser context。
- **运行时改动**(`ouuut-runtime.mjs`):新增可选入参 `archive` 与 `sessionProfileId`;
  有 `archive` 时 `profiles` 取自它;`sendCDPMessage` 在 **user-control 门之后、cdpGuard 之前**
  过 `archive.checkCookieCommand({ sessionProfileId, method, params })`,违规 → `ISOLATION_VIOLATION`
  走 `onSendCDPMessageError` 且**不许发出去**;对外暴露 `runtime.cookiesFor(id)`。
- **CLI 改动**(`ouuut.mjs`):起浏览器后调 `openSessionProfiles(...)`,把结果接进 runtime;收尾时 `dispose()`。
- **验收(可复现)**:
  1. 新测试 `native/binding/session-profiles.test.mjs`:假对端实现 `Target.createBrowserContext` / `disposeBrowserContext`,
     断言 persona 用 `disposeOnDetach:false`、disposable 用 `true`;**同一会话里两条档案的 cookie 池互不可见**;
     不带 `browserContextId` 的 `Storage.getCookies` 被 `ISOLATION_VIOLATION` 拦下;
     disposable 在 `dispose()` 后 context **真被销毁**。
  2. Windows 全量**不红**(既有 306 条不许为了新功能放宽)。
- **实际完成情况**:
  - 新模块 `native/binding/session-profiles.mjs`;运行时接 `archive`/`sessionProfileId`(发送路径在 **user-control 门之后、cdpGuard 之前**过闸);
    CLI 起浏览器后接线、收尾 `await dispose()`(成败都走)。假对端扩展了 browser context 与**按 contextId 分池**的 cookie,
    与「省略即落默认池」的 #319 行为一致。
  - **测试**:`316/316`(既有 306 + 新增 10 = 7 条接线 + 3 条 real 寻址),零红;既有断言一条未改。
  - **接线时抓到一处只有真机才暴露的缝隙(已修)**:`real` 的寻址方式是**省略** `browserContextId` ——
    Chrome 的默认 context **没有 id**。真机实测(Chromium 156):省略 OK;传 `"default"` 被拒
    (`Failed to find browser context for id default`);传假 id 同样被拒。
    修法:`archive.mjs` 把 real 的簿记值规范成 `null`(= 省略),句柄对 real **不发**该参数,闸对 real **反过来要求必须省略**。
  - 附属决定(逐条记下,便于后人复核):① `kind` 缺省时 `archive` 为 `null` —— 这是"与今天逐字节一致"的唯一结构性做法;
    ② 闸的触发条件是 `archive && sessionProfileId`;③ `cookiesFor` 的 send 回调用 `cdp.send`(要那条响应)而不是 `sendRaw`;
    ④ real 会话里**只有** real 一条档案(没给档案目录时不冒充 real)。
  - **没做**:多 persona 池、按档案绑代理(P3)、把 F5 的 seed 画像注入 browser context。

### P2b · Linux 上三种档案实测 —— ✅ **已完成(2026-10-25)**

- **验收结果**(真 Chromium `156.0.8078.47` @ `vps-jp`,三种 kind 各起一次;`$HOME/ouuut-p2-<kind>`):

  | kind | `listProfiles()` | 本档案寻址值 | 闸:省略 / 带自己的 id / 带别人的 id | `dispose()` 后 context |
  |---|---|---|---|---|
  | `persona` | `real` + `persona` | 真 context id | **BLOCK** / ALLOW / **BLOCK** | **还在**(长期画像要留着) |
  | `disposable` | `real` + `disposable` | 真 context id | **BLOCK** / ALLOW / **BLOCK** | **已消失** ✓ |
  | `real` | **只有 `real`** | `null`(= 省略) | ALLOW / — / **BLOCK** | 无 context 可销(默认 context 不参与) |

- **跨档案隔离(真浏览器)**:在 persona 的 context 里写入 cookie 后,
  persona 的 jar = `["only_persona"]`,**real 的 jar = `[]`**;disposable 同理。**池是真的分开的。**
- **CLI 通路也验了**(不只是直接调模块):`node native/bin/ouuut.mjs nodejs --headless --profile-kind persona|disposable`
  → `listProfiles()` 分别是 `{id:"persona",kind:"persona"}` / `{id:"disposable",kind:"disposable"}`,快照 397 字符含 `hello ouuut`。
- **残留(照实记)**:CLI 通路的 `real` **没在 Linux 上跑** —— 按设计它必须同时给档案目录,而本机 shell 侧有浏览器参数守卫
  会拦那个字面量;`real` 的**模块级**运行已在 Linux 上验过(上表),CLI 侧只有 `parseArgs` 的校验用例覆盖。

### P3 · 档案绑代理 + 轮换 + 脱敏(F13)

- 现状只有一个全局 `--proxy` 透传(`native/bin/launch-args.mjs:154/273-275`),**档案对象里没有 proxy 字段**。
- 做法:`archive.mjs` 的 `normalizeProfile()` 加 `proxy`(socks5/http + 可选凭据);启动时按档案挂载;
  `planUpdate`/日志/诊断输出统一过 `redactProxy()`;**轮换只允许 `disposable`**,且 CLI 必须显式开启。
- 约束:ADR-013 —— **轮换池禁用于对照实验**,只能用于生产用途。
- **验收**:两个档案并发,各自出口 IP 探针不同;`grep` 全部日志与错误消息,无 `user:pass@` 形态。

### P4 · 出口一致性闸(F6)

- 现状:`fingerprint.mjs` 已保证「国家/时区/语言同源」,但**没有任何地方比对出口 IP 地理**。
- 做法:启动前查出口国家(优先**离线 GeoIP 表**,避免每次联网 + 避免把出口信息发给第三方),
  与画像 `country` / `timezone` 不一致 → **拒绝启动**,错误码 `OUUUT_EGRESS_MISMATCH`;
  显式越权开关 `--allow-egress-mismatch`(给了才放行,且在诊断里标红)。
- **验收**:用已实测的 `pin-jp-41105`(JP 机房,`161.33.5.222`)+ 美国画像 → 必须拒绝;
  换成日本画像 → 放行。**「该拒绝时拒绝」和「该放行时放行」两条都要有**。

### P5 · 三入口(F14)

- 现状:只有 CLI(`native/bin/ouuut.mjs`)。全仓无 MCP server、无 HTTP 服务。
- 做法:新增 `native/serve/http.mjs`(HTTP/WS)与 `native/serve/mcp.mjs`(MCP stdio),
  **共用** `orchestrator.mjs` + `task-spaces.mjs`;**编排放后端,浏览器保持薄**(借 ego 的形状)。
  MCP 只需最小 JSON-RPC,不引新依赖。
- **验收**:同一段任务(goto example.com + snapshot)经三条入口驱动,快照文本一致。

### P6 · 分发形态定案(需用户拍板)

- 事实:`dist/ouuut-0.1.3-win-x64/payload` 里 **`*.mjs` = 0 个**,JS 跑的是仓库侧 `native/` ——
  现在交付的是「浏览器 + 仓库侧 JS」的组合,不是单文件分发。这条必须在发版前钉死。
- 两个候选:
  - **A. 单文件**(推荐):esbuild 把 `native/` 打成单个 `ouuut.mjs`,与浏览器 payload 同目录发布。
    第三方要的是「一个 tar + node」,不要仓库。
  - **B. 保持组合**:零打包成本,但第三方必须拿整仓,且「可复现构建」的交付物说不清。
- 拍板后记 **ADR-017**。

### P8 · 检测基准收尾(M4/M0)

- **`creepjs` 判据自洽性复核(必做,不是可选项)**:`probe/out/20261024-033825` 那一轮里

## 五、仍然不做

引用 `docs/功能范围.md` §二(红线 N1–N5、战略 N6–N14、留接口 N15–N20)。
本方案**额外明确三条**,防止「单机替代」被执行成别的形状:

1. **不为跨平台写第二套内核补丁**。POSIX 只做通道(P1),内核补丁(0001/0002/0004)维持 Windows。
   Linux 侧跑的是**该平台的 Chromium**,检测分数**不作为** Linux 的验收判据。
2. **不为「可复现」放宽判据**。R1 只能证明 R1 能证明的;R2 没做就照实写没做。
3. **不买机器、不租云机**。P1–P12 全部在已有设备上闭合;若真出现买机器才行的结论,先回头查是不是工具问题。
