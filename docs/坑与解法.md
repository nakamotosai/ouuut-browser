## 坑-1 · `bash` 指向 WSL 启动器

- **现象**:`i/o error: stream did not contain valid UTF-8`;或直接吐出 WSL 的
  「适用于 Linux 的 Windows 子系统没有已安装的分发」中文提示(乱码);
  同时 `chmod` 等命令报 `command not found`
- **根因**:系统 PATH 里的 `bash` 解析到 WSL 的启动器,不是 Git Bash
- **正解**:显式调用 `"C:/Program Files/Git/bin/bash.exe"`
- **复现记录(2026-10-24)**:同一个会话里,**前面多次 `bash` 调用走的是 Git Bash,
  中途突然变成 WSL** —— 说明这不是「装没装对」的静态问题,而是**每次调用都可能不同**。
  凡是**脚本语法检查 / 需要 chmod / 需要 Unix 语义**的调用,**一律写全路径**:
  ```bash
  B="C:/Program Files/Git/bin/bash.exe"
  "$B" -c 'bash -n tools/20-rebase.sh && echo OK'
  ```
  这样即使外层 shell 变了也不受影响。已被 `tools/20-rebase.sh --dry-run` 的冒烟测试验证。

## 坑-5 · `secrets_manager.py read` 的两个陷阱

- **陷阱 1:两个命令返回结构不同**
  - `read <service>` → `{"service", "num_keys", "keys": {...}}`
  - `read <service> <key>` → `{"service", "key", "value"}`
- **陷阱 2:`read <service>` 里的 value 是【打码】的**
  - 整服务读出的值形如 `http...7081` / `b602...1a53`(定长 11 字符),**不是真值**
  - 照着它去请求 → `ValueError: unknown url type: 'http...7081/api/v1/user'`
- **正解**:要真值一律 `read <service> <key>` 然后取 `['value']`;
  整服务读只用来**列 key 名**

## 坑-10 · Playwright `ignore_default_args=True` 会让浏览器起不来

- **现象**:
  - `ignore_default_args=True` + `channel="chromium"` → `TargetClosedError: Target page,
    context or browser has been closed`(日志显示 `<launched> pid=...` 后立刻 graceful close)
  - `ignore_default_args=True` 不加 channel → `Timeout 20000ms exceeded`(headless-shell
    起来了但 Playwright 连不上)
- **根因**:`True` 会把 Playwright 自己**运行所必需**的开关一起丢掉(含 `--headless` 之类),
  不是「只丢它列在文档里的那些」
- **正解**:给**具体名单**,只丢你确实不想要的:
  ```python
  ignore_default_args=["--disable-ipc-flooding-protection",
                       "--disable-popup-blocking",
                       "--enable-unsafe-swiftshader"]
  ```
  `--remote-debugging-pipe` 是**独立追加**的,不受此项影响,所以连接本身没问题
- **同时**:`channel="chromium"` 才会用完整 Chromium(默认走的是 `chrome-headless-shell`,
  UA 里写 `HeadlessChrome` 且没有 `window.chrome`)

## 坑-13 · JS 正则 `\S` 吃不掉 emoji(代理对)

- **现象**:`bot-detector` 探针里 `td.innerText.match(/^(\S)\s+(.*)$/)` 对 `"⚪️ dummyFn"` 成功,
  但对 `"🔴 runtimeEnableLeak"` 失败 —— 结果 `mark` 为空、整个 emoji 留在 `name` 里,
  12 项测试全被归为 `unknown`,整条结果 `error`
- **根因**:`⚪`(U+26AA)是**单个 UTF-16 码元**;而 `🔴`(U+1F534)是**代理对**。
  正则不带 `u` 标志时 `\S` 只匹配一个码元 = 高代理项,后面接的不是空白 → 匹配失败
- **正解**:别用正则取 emoji。按第一个空格硬切:
  ```js
  const sp = s.indexOf(' ');
  const mark = sp < 0 ? '' : s.slice(0, sp);
  const name = sp < 0 ? s : s.slice(sp + 1).trim();
  ```
  Python 侧再 `str.replace("\ufe0f", "")` 去变体选择符
- **教训**:**先看原始证据再下结论** —— 这一轮 5 个 target 全部 `error`,
  若不看 `detail.tests` 就会误判成「浏览器起不来」

### 附:同一类错误还有第二个版本 —— 用文本正则判成败

- **现象**:`bot-detector` 探针的第一版用关键词正则判「失败」,
  正则会命中 `patchright` 那一行的 **`"No leak detected."`** 里的 `detected` →
  把一个**通过**判成**失败**
- **正解**:**优先解析结构化的状态信号**。该站每行首字符就是它自己的判定
  (红/黄/绿/白圆),直接读符号,不要用自然语言猜
- **通用原则**:凡是要写「判定」的地方,先问一句
  ——「这个结论是**站点告诉我的**,还是**我用正则猜的**?」优先用前者。
  猜出来的判定在跨版本、跨语言、跨措辞时会静默错,而且错得没有痕迹

## 坑-15 · Windows Git Bash 下「同一个目录」有两种字符串写法,比较必然失败

- **现象**:脚本里的守卫 `[ "$TOPLEVEL" = "$SRC_DIR" ]` 在 Windows 上**恒为假**遍历:
  - `pwd`(以及 `REPO_ROOT="$(cd … && pwd)"`)→ **POSIX 形**:`/f/projects/ouuut-browser`
  - `git rev-parse --show-toplevel` → **盘符形**:`F:/projects/ouuut-browser`
  - 两者指向**同一个目录**,但字符串永不相等
- **后果(实际踩到)**:**fail-closed 的守卫变成「永远拦下」** ——
  `tools/20-rebase.sh` 在非 dry-run 下永远在阶段 1 中止,而错误信息还说「chromium/src 没建好」。
  更糟的是:**危险情形(src 不是自己的工作树)与正确情形走同一条 die 分支**,守卫完全失去分辨能力。
  而 dry-run 分支只打印不比较,所以**冒烟测试抓不到**
- **正解**:任何路径比较前先归一化,且统一用 `pwd -P`:
  ```bash
  norm() { ( cd "$1" 2>/dev/null && pwd -P ); }   # 两边都过一遍再比
  [ "$(norm "$A")" = "$(norm "$B")" ] || die "..."
  ```
  另:先加一条与路径无关的直判更稳 —— `[ -d "$SRC_DIR/.git" ]` 就能拦住「git 会向上找到外层仓库」
  这个真正的危险
- **教训**:Windows 上的 shell 脚本,**「路径看起来一样」不等于「字符串一样」**。
  凡是拿路径做相等判断的地方,都要问一句「这两边是同一个编码体系吗」。

## 坑-16 · Windows PowerShell 5.1 把 UTF-8 无 BOM 的 `.ps1` 当 ANSI 读 → 整个脚本解析失败

- **现象**:`tools/00-bootstrap-toolchain.ps1` 用 Windows PowerShell 5.1 跑,
  直接吐一屏语法错误:
  ```
  表达式或语句中包含意外的标记“$What”。
  语句块或类型定义中缺少右“}”。
  ```
  报错里引用的源码片段是**乱码**(`throw "$What 澶辫触(exit ...)"`)。
  **而且外层 shell 看到的退出码是 0**(因为管道末端是 `tee`),不留意就会以为跑成功了
- **根因**:该文件是 **UTF-8 无 BOM**,里面写了中文。PowerShell 5.1 对**无 BOM 的 `.ps1`
  默认按 ANSI(本机 GBK)解码** → 中文字节被解成乱码 → 字符串字面量提前被某个乱码字节**
  终止 → 后面的中文变成裸 token → 语法树整个崩掉
- **为什么危险**:① 脚本**一行都没执行**(不是「跑了一半失败」),但退出码看着像成功;
  ② 报错文本本身是乱码,不看原文根本不知道是编码问题;
  ③ 这种失败**与脚本逻辑无关**,改逻辑多少次都没用
- **正解**:让 `.ps1` **纯 ASCII**(注释与提示语都写英文),把中文说明放到 `.md` 里。
  这比「加 BOM」更稳 —— 加 BOM 一旦被某个编辑器/工具重新保存为无 BOM 就会复发,
  而纯 ASCII 没有可失败的编码假设
- **验证手法**(值得固化成习惯):改完 `.ps1` 先只做**解析**检查,不要直接跑:
  ```bash
  powershell -NoProfile -Command "\$e=\$null; [void][System.Management.Automation.Language.Parser]::ParseFile('X.ps1',[ref]\$null,[ref]\$e); if(\$e.Count){\$e[0].Message}else{'PARSE OK'}"
  python -c "d=open('X.ps1','rb').read(); print('非 ASCII 字节:', sum(1 for b in d if b>127))"
  ```
- **附带**:`ps1 | tee log` 会吞掉真实退出码 —— 要判成败就用 `${PIPESTATUS[0]}` 或先重定向到文件再单独读 `$?`

## 坑-17 · `/f/...` 只被 bash 内建认,原生 Windows 程序会当成 C 盘路径

- **现象**:`git clone <url> /f/depot_tools` 报 `Cloning into '/f/depot_tools'...` 且 rc=0,
  但 `/f/depot_tools` 与 `F:/depot_tools` **都看不到内容**。实际落点是 **`C:\f\depot_tools`**
- **根因**:**本机的 bash 有两套路径写法,归属还不一致**
  - `bash` 内建(`[ -d ]`、`ls`、`cd`)认 POSIX 形 `/f/...`
  - 而**原生 Windows 程序**(`git.exe` 等)把 `/f/...` 当成「当前盘根下的 `f\...`」
    → cwd 在 C: 上时就成了 `C:\f\...`
  - 更麻烦的是**两个 shell 的 `pwd` 还不一样**:隐式 shell 给 `F:\projects\x`(反斜杠),
    显式 `"C:/Program Files/Git/bin/bash.exe"` 给 `/f/projects/x`
- **为什么危险**:命令**返回 0**、目标看起来「创建成功」,但东西落在完全不相干的位置。
  排查成本极高(本项目为此花了数轮)
- **正解**:
  1. **交给原生工具(git / gn / autoninja / gclient / cl.exe)的路径一律先归一化成 Windows 形**:
     ```bash
     winpath() { command -v cygpath >/dev/null 2>&1 && cygpath -w "$1" || printf '%s' "$1"; }
     REPO_ROOT="$(winpath "$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)")"
     ```
  2. **PATH 里加 depot_tools 时给 POSIX 形**(`/f/depot_tools`)—— 因为 `command -v` 是 bash 内建;
     给 Windows 形会让 `command -v gclient` **找不到**(实测)
  3. 脚本**调用同类工具时一律走显式 Git Bash 全路径**(坑-1 是间歇性的)

## 坑-18 · depot_tools 的工具名在 Windows 上有两套,`command -v` 会挑错

- **现象**:`export PATH="F:/depot_tools:$PATH"` 之后 `command -v gclient` **失败**,
  但目录里明明有 `gclient`、`gclient.bat`、`gclient.py` 三个
- **根因**:① PATH 用了 Windows 形(见坑-17-2);② Windows 上 depot_tools 把每个工具
  同时提供为「无扩展名脚本」与「`.bat` 包装」,而 **`.bat` 才会自己摆好 python 环境**
- **正解**:写一个解析器,按平台优先挑 `.bat`,并回退:
  ```bash
  IS_WINDOWS=0
  case "$(uname -s)" in *MINGW*|*MSYS*|*CYGWIN*|Windows_NT) IS_WINDOWS=1 ;; esac
  resolve_tool() {
    local cands c
    if [ "$IS_WINDOWS" -eq 1 ]; then cands="$1.bat $1"; else cands="$1 $1.bat"; fi
    for c in $cands; do command -v "$c" >/dev/null 2>&1 && { printf '%s' "$c"; return 0; }; done
    return 1
  }
  GCLIENT="$(resolve_tool gclient)"   # → gclient.bat
  ```
  另外 **`gn` / `autoninja` / `ninja` 在 depot_tools 第一次跑之前不存在** ——
  它们由 `gclient` 自己 bootstrap 出来,所以 sync 之后要**再解析一次**
- **附带**:Chromium 构建必须设 `DEPOT_TOOLS_WIN_TOOLCHAIN=0`,否则 depot_tools 会去抓
  Google 内部的 hermetic toolchain(非 Googler 抓不到)

## 坑-20 · `chromium.googlesource.com` 按 IP 限流(429),批量克隆必踩

- **现象**:`gclient sync` 拉到一半挂掉,报
  ```
  fatal: unable to access 'https://chromium.googlesource.com/external/github.com/google/pthreadpool.git/':
      The requested URL returned error: 429
  remote: RESOURCE_EXHAUSTED: Resource has been exhausted (e.g. check quota)
  remote:   subject: "shared/shared_anonymous"
  remote:   description: "Short term server-time rate limit exceeded"
  ```
  同时前面还有一堆 `WARNING: subprocess ... failed; will retry after a short nap...`
- **误判陷阱(重要)**:单看现象很容易以为「网络慢/不通」。我最初就是这么判的 ——
  实测 `git clone` 那个大仓库 **75 秒零字节增长**(TCP 已建立、CPU 近乎 0),
  于是去测速、换源。**其实根因是限流**,不是带宽。
  - 判别方法:同一时刻跑一个**小请求**(`git ls-remote --heads <url>`)——
    若它秒回,就说明「不是不通,是批量请求被限」
- **正解(三条一起上)**:
  1. **把 GitHub 出身的依赖改走 GitHub** —— `external/github.com/<org>/<repo>` 这类
     路径本来就是从 GitHub 镜像过去的,重写回去既快也不吃 Google 配额:
     ```bash
     git config --global --add url."https://github.com/".insteadOf \
         "https://chromium.googlesource.com/external/github.com/"
     git config --global --add url."https://github.com/webmproject/".insteadOf \
         "https://chromium.googlesource.com/webm/"
     git config --global --add url."https://github.com/".insteadOf \
         "https://chromium.googlesource.com/v8/"
     ```
     注意 `insteadOf` 用**最长前缀匹配**,所以针对性规则是安全的;
     **别**写一条 `.../ -> github.com/` 的泛规则(会把 `chromium/src.git` 也改坏)
  2. **外层包重试**:`gclient` 自己重试几轮后会放弃;`gclient sync` **幂等**,
     所以外层退避重跑是安全且有效的
  3. **必要时换出口 IP** —— 限流是按 IP 的
- **附带发现**:`chromium.googlesource.com` 上的大仓库克隆在本机基本不可用,
  **`github.com/chromium/chromium` 镜像**实测 25 秒下 179 MB(≈7.2 MB/s)。
  所以薄脚本里源码来源默认用 GitHub 镜像(见 `tools/10-fetch-chromium.sh` 的 `SRC_URL`)
- **⚠️ 镜像重写有一个副作用,必须知道**:`external/github.com/<org>/<repo>` **不一定**是
  1:1 的 GitHub 仓库 —— 有的指向**子目录**。实测踩到:
  ```
  chromium.googlesource.com/external/github.com/SeleniumHQ/selenium/py.git
      → 重写成 https://github.com/SeleniumHQ/selenium/py.git → not found
  ```
  而 `gclient` 会因为这个 dep 失败而**整个 sync 报错退出**。
  **修法**:在 `.gclient` 的 `custom_deps` 里把它设成 `None` 跳过
  (构建 Chrome 不需要 WebDriver 的 python 绑定)。
  **通用教训**:做**批量 URL 重写**时,一定要先确认「重写后的目标集合 ⊇ 重写前用到的所有路径」;
  做不到就必须**准备跳过名单**,并让失败可见 —— 不要让一个边角依赖拖垮整个流程。
  **别手工维护这个名单**:写个预检工具,跑一次
  **`tools/preflight-deps-mirror.py`** —— 它解析 `src/DEPS`,
  对每个 googlesource 依赖算出重写后的 URL 并 `git ls-remote` 探活,
  **直接输出可粘进 `.gclient` 的跳过块**。实测一次抓出 **10 个**不可达依赖,
  其中 **7 个是 LLVM monorepo 的子目录**
  (`libc++` / `libc++abi` / `libunwind` / `compiler-rt` / `llvm-libc` / `libFuzzer` / `clang-format`),
  另 3 个是 `v8/fuzzer_wasm_corpus`、`google/cld_3`、`SeleniumHQ/selenium/py`。
  **一个个追会追到天亮 —— 这一类问题要用工具一次解决,而且要能重复跑**
  (每换一个 Chromium 版本都要重跑:`10-fetch-chromium.sh` 已自动接线)
- **✅ 最终解法:能修源就别丢依赖 —— 「更长的恒等规则」表达排除。**
  `insteadOf` 用**最长前缀匹配**,所以给不适配的子树加一条**更长的、映射到自己的**规则,
  那个子树就**留在 googlesource** 上(那些合成仓库在 GitHub 上根本不存在):
  ```
  url."https://github.com/".insteadOf                      ".../external/github.com/"
  url.".../external/github.com/llvm/".insteadOf            ".../external/github.com/llvm/"
  url.".../external/github.com/SeleniumHQ/".insteadOf      ".../external/github.com/SeleniumHQ/"
  url.".../external/github.com/google/cld_3.git".insteadOf ".../external/github.com/google/cld_3.git"
  ```
  **效果**:可达率从 **60/70** 变成 **144/144**,跳过名单从 **10 条变成 0 条** ——
  `libc++` / `compiler-rt` / `libunwind` / `llvm-libc` 这些组件**一个都没丢**,
  而是从它们真正存在的地方拉。
  **比「跳过」好在哪**:跳过 = 永久丢失组件 + 多一份要维护的名单;
  修源 = 保住组件 + 名单为空。
- **精确到什么粒度**:`cld_3` 那条必须**精确到整条 URL** ——
  googlesource 上的合成仓库名是 `google/cld_3`,GitHub 上是 `google/cld3`(无下划线);
  但又**不能**排除整个 `google/`,因为同子树下的 `google/pthreadpool` 在 GitHub 上真实存在。
  **规则粒度要跟着事实走,不能图省事。**
- **通用教训**:**同一个错误第二次出现时,不要再修那一个实例,去修那个类。**
  我在这里先追了三个实例(v8 规则、Selenium、llvm clang-format)才写预检工具;
  写完一次就拿到了全部 10 个。而更关键的一步是**再往后一层**:
  发现「10 个都该修源而不是跳过」,于是跳过名单归零。
- **效果**:加上重写之后,**429 出现 0 次**,sync 一路推进到 100 万文件 / 19 GB
- **⚠️ 重写规则的三个陷阱(全是实测踩出来的)**:
  1. **别映射到没有 org 的前缀**。`:…/v8/` 直接映射到 `github.com/` 会得到
     `github.com/v8.git`(**不存在**);正确写法是映射到 `github.com/v8/`
     → `…/v8/v8.git`。**规则改完要按实际路径手推一遍**。
  2. **`external/github.com/<org>/<repo>` 不一定是 1:1 仓库**(可能指向子目录),
     这类要靠 `.gclient` 的 `custom_deps` 设 `None` 跳过。实测踩到两个:
     `SeleniumHQ/selenium/**py**`、`llvm/llvm-project/**clang/tools/clang-format**`。
     **一个 dep 失败会让整个 `gclient sync` 退出** —— 所以跳过名单必须齐全
  3. **别用 `git config --global` 写这些规则,用 `GIT_CONFIG_COUNT/KEY_n/VALUE_n` 环境变量**:
     - 只对本次进程及其子进程生效,**不污染用户的全局 gitconfig**
     - **不会留下旧规则** —— 写成 `--global` 之后,规则改一版就残留一版
       (实测:那条错的 v8 规则留在全局配置里,让我多排查了一轮)
     - 作者/CI 拿到脚本就能复现,不需要先跑一遍「配置命令」
     ```bash
     export GIT_CONFIG_COUNT=3
     export GIT_CONFIG_KEY_0="url.https://github.com/.insteadOf"
     export GIT_CONFIG_VALUE_0="https://chromium.googlesource.com/external/github.com/"
     ...
     ```
- **附带**:gclient 在「克隆失败 → 把冲突目录移到 `_bad_scm/` → 再试」这条路径上,
  如果目录**已经被移走过**,第二次 move 会抛 `FileNotFoundError` 而**不是**继续重试。
  所以失败后重跑前,清掉 `chromium/_bad_scm` 与残留的 `src/_gclient_*` 更省事

## 坑-21 · 让 Chromium 的 Windows 工具链认账(一次踩齐五关)

`gn gen` 从「完全跑不动」到 `Done. Made 36194 targets from 5059 files`,中间卡了五处。
**每一处都是「上游假设了某件事,而本机不是那样」** —— 记全,免得重建时再走一遍。

### 关 1 · VS 装在 `Program Files (x86)`,而 Chromium 只找 `Program Files`

- **报错**:`Exception: No supported Visual Studio can be found. Supported versions are: 18.0 (2026), 17.0 (2022), ...`
- **根因**:`build/vs_toolchain.py` 的 `_GenerateCandidatePaths()` 只枚举
  `%ProgramFiles%\Microsoft Visual Studio\2022\<版本>`(Enterprise/Professional/Community/Preview/Insiders/**BuildTools**)。
  本机用 bootstrapper 装的是 **`C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools`**
- **另一个坑**:`vswhere -products *` **看不到这个实例**(实例注册缺失),
  所以「vswhere 查得到」不是可靠判据 —— 要查 `cl.exe` 与 SDK 目录**实体**
- **正解**:设环境变量 **`vs2022_install`**(`_GenerateCandidatePaths` 第一项就查它):
  ```bash
  export vs2022_install="C:\\Program Files (x86)\\Microsoft Visual Studio\\2022\\BuildTools"
  ```

### 关 2 · SDK 版本被**硬钉死**,而且钉在两个地方

- **报错**:`Path "C:\Program Files (x86)\Windows Kits\10\\include\10.0.28000.0\\um" ... does not exist`
- **根因**:上游把 SDK 版本写成常量 **`10.0.28000.0`**,**两处**各一份、都无兜底:
  - `build/vs_toolchain.py` → `SDK_VERSION`
  - `build/toolchain/win/setup_toolchain.py` → `SDK_VERSION`
  而本机只有 **`10.0.26100.0`**;28000 不是 VS 2022 的可用组件
  (`vs_installer --add ...Windows11SDK.28000` 返回 **87 无效参数**)
- **修法**:补丁 `0003-vs-toolchain-sdk-version-env.patch` 把两处改成
  `os.environ.get('OUUUT_WINDOWS_SDK_VERSION', '<上游原值>')` —— **不设环境变量时行为与上游完全一致**
- **教训**:改一处不够 —— **同一个常量可能在多个文件里各有一份**。
  我改了第一处、重跑仍是 28000,才去 grep 第二处

### 关 3 · Chromium 的「手动指定 VS」分支**上游客就是坏的**

`build/config/win/visual_studio_version.gni` 的 `declare_args()` 提供
`visual_studio_path` / `visual_studio_version` / `wdk_path` / `windows_sdk_version`,
看起来可以完全绕开自动探测。**但那条分支是坏的**:
`else` 分支把 `visual_studio_runtime_dirs` 设成**列表**,而
`build/toolchain/win/win_toolchain_data.gni` 要**字符串** → `gn gen` 报 `This is not a string`。

- **正解**:**别走那条分支**。用关 1 + 关 2 的两个环境变量,让**自动探测路径**工作。
  (顺带:`wdk_path` 在整棵树上**只用于那个 assert**,没有真实消费者)

### 关 4 · 缺 "Debugging Tools for Windows"

- **报错**:`dbghelp.dll not found in "...\Windows Kits\10\Debuggers\x64\dbghelp.dll"`
- **根因**:`vs_toolchain.py` 的 `_CopyDebugger()` **硬要求** SDK 的 Debugging Tools 特性,
  而 VS 的 `Windows11SDK.26100` 组件**不含**它;VS 的 catalog(19354 个包)里也**没有**单独的 debuggers 组件
- **它只要一个文件**:`debug_files` 里只有 `dbghelp.dll` 是必需(`dbgcore.dll`/`symsrv.dll` 可选),
  `msdia140.dll` 从 VS 的 DIA SDK 取(本机有 ✅)
- **正解(已采用)**:SDK **自己**的 `App Certification Kit` 目录里就有 `DbgHelp.dll` 与 `symsrv.dll` ——
  把它们放到 SDK 期望的路径:
  ```powershell
  $d='C:\Program Files (x86)\Windows Kits\10\Debuggers\x64'
  New-Item -ItemType Directory -Force $d
  Copy-Item 'C:\Program Files (x86)\Windows Kits\10\App Certification Kit\DbgHelp.dll' "$d\dbghelp.dll"
  Copy-Item 'C:\Program Files (x86)\Windows Kits\10\App Certification Kit\symsrv.dll'  "$d\symsrv.dll"
  ```
  **更正规的修法**:装 Windows SDK 的 "Debugging Tools for Windows" 特性
  (`winsdksetup.exe /features OptionId.WindowsDesktopDebuggers`)——
  但当前官方 fwlink 已失效/被改指别处,没走通。**权宜的性质要写清楚**:
  它只影响最终放进输出目录的 `dbghelp.dll`(用于符号化),**不影响编译**

### 关 7 · 缺 ATL 组件(`atldef.h` not found)

- **现象**:构建跑到 **4750 步**(10 分钟)才失败:
  `base/win/atl_throw.h(35,10): fatal error: 'atldef.h' file not found`
- **根因**:`Microsoft.VisualStudio.Component.VC.ATL` **不在** `--includeRecommended` 里 ——
  所以按「VCTools + includeRecommended」装的 BuildTools **没有 ATL**。
  而 Chromium 的 `base/win/atl_throw.h` 直接 `#include <atldef.h>`
- **修法**:`vs_BuildTools.exe --quiet --wait --norestart --nocache --add Microsoft.VisualStudio.Component.VC.ATL`
  (已补进 `tools/00-bootstrap-toolchain.ps1`)
- **⚠️ 附带发现(重要)**:`vs_installer.exe modify --installPath ... --add ...` 在本机
  **返回 87(无效参数)** —— 日志里它打印的是**用法帮助**,即它没认出这条命令。
  根因是**这个 VS 实例没有正确注册**(注册表 `HKLM\SOFTWARE\Microsoft\VisualStudio\Setup`
  的 `instanceIds` 为空 —— 这也解释了为什么 `vswhere -products *` 看不到它)。
  **但 bootstrapper(`vs_BuildTools.exe --add ...`)能成** —— 它自己处理注册与依赖解析。
  **结论:补装 VS 组件优先用 bootstrapper,不要用 `vs_installer modify`。**

### 关 5 · `PYTHONUTF8=1` 会把构建打死在一个 ACL 动作上

- **报错**:`UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd2 in position 698`
  来自 `build/win/set_appcontainer_acls.py` → `testing/scripts/common.py` 的 `set_lpac_acls()`
- **根因**:那里用 `subprocess.check_output(['icacls', dir], universal_newlines=True)`
  **没指定编码**,于是跟随 Python 的文本编码;而本机环境里设了 **`PYTHONUTF8=1`**,
  Python 就用 UTF-8 去读 `icacls` 的 **GBK(中文)** 输出 → 崩
- **正解**:**构建前 `unset PYTHONUTF8 PYTHONIOENCODING`** —— 让 Python 用本机 locale,
  与系统工具一致。**不需要改 Chromium 一行代码**
- **通用教训**:在中文 Windows 上跑「假设输出是 UTF-8」的构建脚本,
  `PYTHONUTF8=1` 是**反效果**的。这类变量通常是别处为了让 Python 自己输出 UTF-8 而设的,
  却会破坏它**读**子进程输出的行为

### 关 6(不是工具链,但同一段踩的)· 有 `.git` 但工作区为空的依赖,`gclient` 永远不会补

- **现象**:`gn gen` 通过,`autoninja` **9.7 秒**就失败:
  `"../../third_party/pthreadpool/src/src/fastpath.c" ... missing and no known rule to make it`
- **根因**:该依赖**首次克隆被 429 打断**,留下一个有 `.git` 但**零文件**的目录。
  `gclient sync` 看到 `.git` 就当它「已完成」,**后续每次 sync 都跳过它** ——
  于是永远不会自愈,直到构建报缺文件
- **正解**:删掉那个 `src` 目录,再 `gclient sync`(实测 18 秒补完,44 个文件)
- **工具化**:`tools/find-dirty-deps.sh` **已扩展为同时检查这一类** ——
  扫 `chromium/src` 下 4 层内所有子仓库,`ls-files` 计数为 0 即「空/残缺」,
  与「脏」一起报告/清理。**实测:135 个子仓库里正好 1 个是这种状态**
- **通用教训**:校验**存在性**不够,要校验**完整性**。
  「有 `.git`」不等于「拉完了」;「仓库可达」不等于「有那个 revision」(见坑-20)。
  **同一个道理我在这一轮踩了两次。**

## 坑-22 · 浅克隆里 `git fetch --tags` 会去拉**整棵 chromium 历史**(29,397,996 个对象)

- **现象**:`tools/20-rebase.sh` 停在 2/7,**50 分钟毫无进展**,日志一个字都不涨
  - 附带的假象:`tee` 写文件是**块缓冲**的,所以「日志是空的」**不等于**「它没在跑」。
    别被日志骗了,去看进程表
- **取证**(掐下进程表才看清):
  ```
  git fetch --tags origin refs/tags/156.0.8078.47:refs/tags/156.0.8078.47
  git index-pack --stdin --fix-thin --pack_header=2,29397996
  ```
  **29,397,996 个对象** —— 那是整棵 chromium 历史
- **根因**:两个条件叠加,单看任何一个都不致命
  1. 本仓库是 **`--depth 1` 浅克隆**(`.git/shallow` 在位;`git rev-list --count HEAD` = **1**)
  2. `remote.origin.fetch = +refs/tags/*:refs/tags/*` —— 见下方「归因更正」
  ⇒ 在浅克隆里,**任何**想补齐历史的 fetch 都会退化成「拉整棵树」;
  而 `--tags` 更是直接把「所有 tag」都变成目标
- **⚠️ 二次伤害,而且是真凶之一**:同一段里 `gclient sync --with_branch_heads --with_tags`
  的 `--with_tags` 是同一个病

- **正解**
  - 目标 tag **已在本地就一个字节都不下载**(实测:首次 rebase 时 tag 与 HEAD 本来就对上了
    —— 「rebase 要下载一堆东西」这个直觉在这里是**错的**)
  - 真要拉,加 **`--depth 1`** 只拉一层
  - **删掉** `--with_tags` / `--with_branch_heads`
  - 一条被忽略的事实:`.gclient` 里 src 是 **`"managed": False`**
    ⇒ **plain `gclient sync` 根本不动 src 的 git 状态**,只按当前 src 的 DEPS 同步依赖。
    那两个 `--with_*` 纯属多余且致命
- **代价**:掐掉时 F: 尚余 502 GB —— **运气好**。
- **通用教训**:浅克隆仓库里 `fetch` 的代价**不是「增量」而是「补齐整个历史」**。
  想知道它到底要下多少,**看 `--pack_header=<n>` 里的 n**,别等它跑完。
  更根本的一条:**按下回车前,先想清楚这条命令可能拉多少字节。**

### 归因更正(核验分身纠正,2026-10-24)

本文初稿把 `remote.origin.fetch = +refs/tags/*:refs/tags/*` 写成**「克隆自带的既有条件」**。
**那是错的** —— 核验用**仓库外对照实验**反证:

| 做法 | 写出的 `remote.origin.fetch` |
|---|---|
| `git clone --branch <tag> --depth=1` | `+refs/tags/<tag>:refs/tags/<tag>`(**只有单个 tag**) |
| `gclient sync --with_branch_heads --with_tags` | **追加** `+refs/branch-heads/*:refs/remotes/branch-heads/*` 与 `+refs/tags/*:refs/tags/*` |

后两条与 `depot_tools/gclient_scm.py` 的 `_SetFetchConfig()` 逐字相同,
且**只在那两个 flag 被传时才写入**。
⇒ 这副「催命 refspec」是我们**自己的脚本灌进去的**,不是克隆给的。

**而且灌它的那行当时还活着**:`tools/10-fetch-chromium.sh:103`(`sync_with_retry()` 内,主路径)。
本坑的修复第一版**只改了 `tools/20-rebase.sh`,漏了它** ——
只要那行还在,**枪每次都会被重新上膛**。现两处都已改为裸 `gclient sync`。

**通用教训**:归因要**做对照实验**,别拿「现状」当「前提」。
`git config` 里的值可以是**任何一次** gclient 调用写进去的 ——
「它现在是这样」不等于「它本来就是这样」。

## 坑-23 · 产物实例还活着 → 链接阶段 `permission denied`(白烧一整轮构建)

- **现象**:构建能跑、编译能过,**只在最后链接那一步**炸:
  ```
  lld-link: error: failed to write output './chrome.dll': permission denied
  4m28.78s Build Failure: 4 done, 1 failed, 678 remaining
  ```
- **根因**:**上一次冒烟起过的产物实例还活着**(实测 12 个进程,父进程 pid 2532),
  它们把 `chrome.dll` 映射住了。构建的其他部分都能跑,只有**写回产物**这一步失败
- **为什么难查**:这是**覆盖写**而不是删除重建 —— 文件在、可读、`sha256sum` 也正常,
  只有在真要写的那一刻才知道被锁
- **正解**:清掉**本项目** out/Release 下的实例(**严格按路径匹配**,
  别误伤用户自己的 Chrome / omp 的 puppeteer):
  ```powershell
  Get-Process chrome -ErrorAction SilentlyContinue |
    Where-Object { $_.Path -like '*ouuut-browser*out\Release*' } | Stop-Process -Force
  ```
  实测清掉 12 个我方进程后 `chrome.dll` 立刻可独占打开;omp 的 puppeteer(12 个)未受影响
- **工具化**:`tools/20-rebase.sh` 的 1/7 已加**前置锁守卫** ——
  用 `[IO.File]::Open(path, 'Open', 'ReadWrite', 'None')` 试独占打开,
  锁着就**在 3 秒内**带着清理命令中止
- **通用教训**:凡是「写回一个**可能正在被使用**的产物」的构建,
  前置检查里都该有锁探测。**把失败从「几分钟后、在最后一步」提前到「3 秒后、在最前面」。**

## 坑-24 · UI 子系统二进制没有 console stdout:`chrome.exe --version` 永远是空的

- **现象**:脚本里 `VER_OUT="$("$CHROME_BIN" --version 2>&1 | head -1)"` 拿到**空**,
  于是 `chrome/UPSTREAM` 里的 `smoke=` 一直是空的 —— 而这一步看起来「跑了、没报错」
- **根因**:`chrome.exe` 是 **GUI(Windows)子系统**可执行文件,**没有附着的控制台**。
  实测:`rc=0`、输出长度 **0**。所以这条路**永远**取不到版本号,不是「偶发」
- **正解**:**读 PE 的版本资源** —— 纯文件级取证,不启动任何进程,也不碰任何 profile:
  ```bash
  powershell -NoProfile -Command \
    "(Get-Item '<chrome.dll 的 Windows 路径>').VersionInfo.FileVersion"
  ```
  实测三份产物(gui 与 dll)一致给出 **`156.0.8078.47`**,与目标 tag 完全对上

## 坑-25 · Windows 路径传给 `sha256sum` 会带回一个 `\` 前缀

- **现象**:`chrome/UPSTREAM` 里出现了
  ```
  artifact_sha256=\a21d0e8ec888b9803629faf87fc7f12308de842962a3f73d598ca5691fc4b555
  ```
  —— 那个**反斜杠不是笔误,是 GNU coreutils 的转义规则**
- **根因**:`sha256sum 'F:\projects\...\chrome.exe'` 中文件名含反斜杠,
  coreutils 认为需要转义,于是整行输出**以 `\` 开头**;`cut -d' ' -f1` 把 `\` 一起切了进来
- **正解**:**用 stdin 喂,别传路径** —— 没有文件名,就没有转义,也就没有前缀:
  ```bash
  sha256sum < "$CHROME_BIN" | cut -d' ' -f1     # ✅ 干净的 64 位十六进制
  ```
- **同一段里的第二个 bug**:`gn_args_digest=$(printf '%s' "$GN_ARGS" | sha256sum …)`
  引用了一个**从未赋值**的 `$GN_ARGS`,在 `set -u` 下报 `GN_ARGS: unbound variable`,
  并把 **sha256(空串)** = `e3b0c442…` 写进了 UPSTREAM —— 一个**看起来合法、实际毫无意义**的摘要
- **通用教训**:摘要字段**错得最隐蔽** —— 它总是「一串十六进制」,形状永远对。
  所以:**凡是摘要,都要能回答「这个值对应的是哪个输入」**;
  空输入能算出合法摘要,正是最危险的地方。

## 坑-26 · Windows 上「fd 3 上挂着待决读」的 Node 进程**退不出去**(`process.exit` 失效)

- **现象**:写 `--remote-debugging-pipe` 通道时,用 Node 做**假 CDP 对端**(从 fd 3 读、往 fd 4 写),
  对端调 `process.exit(7)` —— **stderr 明确打印了「定时器触发 → process.exit(7)」,可进程就是不死**。
  父进程收不到 `exit` 事件,`child.exitCode` 一直是 `null`,存活探测也证明 PID 还在
- **根因**(逐项对照实验,Node 22 / Windows):

  | 组合 | 结果 |
  |---|---|
  | 无 fd3 读流 + `process.exit` | ✅ 退出 |
  | fd3 读流 + **不** attach `data` 处理器 + `process.exit` | ✅ 退出 |
  | fd3 读流 + **attach 了** `data` 处理器 + `process.exit` | ❌ **不退出** |
  | 同上,改用 `process.reallyExit(7)` | ❌ 不退出 |
  | 同上,先 `rs.destroy()` / `rs.pause()` 再 exit | ❌ 不退出 |
  | 同上,改用 **`fs.read` 回调递归**(不建流) | ❌ 不退出 |

  ⇒ 只要 fd 3 上有一个**待决的读**,`process.exit` 与 `process.reallyExit` **都会失效**。
  连 `destroy()/pause()` 都救不回来 —— 所以这不是"流没关干净",而是更底层的东西
- **能用的写法**:只能走 **OS 级强杀**
  ```js
  process.kill(process.pid, "SIGKILL");   // ✅ 实测有效
  process.abort();                        // ✅ 实测有效
  ```
- **影响面**:`native/binding/fixtures/fake-cdp-peer.mjs` 已改用强杀并注明原因。
  **真实产品不受影响** —— 那边 spawn 的是 **Chrome**(原生处理 fd3/fd4,不是 Node 子进程)。
- **通用教训**:拿 Node 当"外部进程替身"时,**"能不能起"和"能不能死"是两件事** ——
  两边都要单独验。我们对通道的收尾有专门用例(`close()` 之后不留活着的子进程),
  正是它把这个问题从"偶发卡住"变成了"指名道姓的失败"。
  **一个不会退出的替身,会让所有"对端死亡"分支永远测不到。**

## 坑-27 · Windows 上 `chrome.exe` **交付后就退 0**,而真浏览器以独立进程树活着

- **现象**:`ouuut nodejs < smoke` 跑到第一次真实 CDP 往返就报
  `task.listTabs: ouuut 退出(code=0 signal=null)—— 未完成的 CDP 请求全部作废`
- **取证(2026-10-25,判别实验)**:

  | 试验 | 我们起的进程 | 我们的 chrome 进程数 |
  |---|---|---|
  | 基线 | — | **0** |
  | 只给档案目录 + `about:blank`(不给 pipe) | 退 0 | **13** |
  | 什么参数都不给 | 退 0 | 23 |

  换成 `Measure-Object -ExpandProperty Count` 才看见真实数量。
- **后果**:`spawnCdpPipe` 把"我们起的那个进程退出"当成"浏览器死了",于是

  ⇒ **`--remote-debugging-pipe` 的 fd3/fd4 只被原始进程持有**,交给别人就没了
- **通用教训**:
  1. **"我们起的进程退出了" ≠ "对端死了"**。长驻服务要先判断"是不是交接",
     再决定要不要作废待决请求。判据不能只看我们手里那个 `ChildProcess`
  2. **孤儿进程要主动清**。这次的清理判据是"Path 落在本仓 `out/Release` 下",
     **绝不能按进程名杀** —— 使用者自己的 Chrome 也叫 `chrome.exe`(实测同机 12 个)
  3. **测量方式本身也会骗人**:同一个问题,`Format-Table | Out-String` 给出 0、
     `Measure-Object -ExpandProperty Count` 给出 22。**"没看到"和"没有"要分开验**

### 补记(2026-10-25 晚):根因找到了 —— **补丁从来没被编译进去**

- **顺带修掉**:`cdp-pipe.mjs` 里组诊断消息的时机从 `exit` 改到 `close`

### 补记三(2026-10-25 11:25):**真凶是提权**,不是开关、不是补丁、不是打包

- **沙箱** → 提权下还有

  ```

  ⇒ ninja 不是看 mtime 判脏,而是**拿「这条命令有没有在 `.ninja_log` 里留下记录」**当依据。
  日志没了,它就认为每一条边都没执行过。
- **`.ninja_log` / `.ninja_deps` 两个文件都不存在**(`ls -a out/Release | grep ninja` 为空)。
  最可能是某次清理把 `out/Release/.*` 一起删了,或产物目录被整体拷贝过。
- **试过且无效**:
  - `ninja -t restat` → 没有日志可 restat,步数仍是 58,504
  - 手工跑 `ninja -t commands` 给出的命令 → 编译那条**能跑**(单文件实测 **40.975 s**),
    但链接那条依赖 `@./chrome.dll.rsp`,而 **`.rsp` 是 ninja 执行时才生成的**,文件不存在 ⇒ 断
- **代价换算**:改一个 C++ 文件本身只要 **41 秒**;剩下的全在链接。
  但日志缺失把成本放大成「44,813 次编译 + 58,504 步」= 数小时。
- **结论 / 纪律**:
  1. **不要每加一个内核补丁就跑一次构建。** 日志缺失期间,任何一次都是全量 ——
     **补丁攒批,一次性构建**。这本来也是里程碑排法:M1 只要求「**具备**可复现能力」,
     真正跑全量 + 跨路径复现是 **M7 分发** 的验收项,不在迭代里。
  2. 想恢复增量,只有让 ninja 自己跑完一次(它会边跑边写日志)。
     **不要手工伪造 `.ninja_log`** —— 哈希/mtime 写错会让 ninja 跳过本该重编的边,
     静默产出错误二进制。这类"看起来成功"的失败比慢更糟。
  3. 以后清理 `out/Release` **只删确定的东西**,别用 `out/Release/.*` 这类通配。

## 坑-31 · POSIX 上「写端」的流错误没挂处理 ⇒ 把诊断冲掉,还把测试进程掀翻

- **现象**(2026-10-25,`vps-jp`,Ubuntu 24.04 / Node v24.22.1):
  同一份代码 Windows 上 `306/306`,Linux 上 `306 条 / 298 过 / 2 红 / 6 跳过`。
  两条红看起来八竿子打不着 —— `cdp-pipe.test.mjs:186`(stderr 要进抛给调用方的错误里)与
  `task-spaces.test.mjs:167`(takeOverTaskSpace 之后门重新打开)—— 但报的是**同一个**东西:
  ```
  Error: read ECONNRESET   { errno: -104, code: 'ECONNRESET', syscall: 'read' }
      at Pipe.onStreamRead (node:internal/stream_base_commons:221:20)
  ```
- **定位**:写了个最小复现,把每条 stdio 上的 `error` 都打出来:
  ```
  stdio[3] error: ECONNRESET read
  ```
  ⇒ 挂在 `child.stdio[3]`(**我们往浏览器写命令**的那一端)上,**没有人挂 `error` 处理**。
  POSIX 上 stdio 索引 ≥3 的 `"pipe"` 是 **socketpair 的两端**(Windows 上是命名管道,不走这条路),
  对端一死这一端就会抛 `ECONNRESET`;Node 对没有处理的 `error` 事件是**直接抛** ⇒ 变成未捕获异常,
  报错归到**当时恰好在跑的那个用例**上(所以两条红看着毫不相干)。
- **为什么不能就地 `failAll`**:对端一死,传输层先炸,而 stderr 往往**还没派发完**;
  抢先把 pending 拒掉,调用方拿到的就是一句裸 `read ECONNRESET` —— 退出码 / stderr / 启动参数
  这些正是**坑-29 花了两小时才换来的诊断**,全丢。
- **正解**(`native/binding/cdp-pipe.mjs`):
  1. **两端都挂 `error`**(读端 stdio[4] 与写端 stdio[3]),语义统一为 `noteTransportError`:**只记不拒**;
  2. 记下的行进 `diagnoseExit()`,所以「只记」不等于「丢掉」;
  3. 拒付仍交给 exit/close 那条路径;若 exit 时已知传输层报过错,**不再等那 2 秒兜底**,当场把诊断交出去。
- **纪律**:跨平台验通道时,**别只看哪条用例红了** —— 先确认「红的是不是同一根因」。
  未捕获的流错误会到处乱窜,把一条 bug 伪装成两条无关的失败。

## 坑-33 · 默认 browser context **没有 id** —— 只能用「省略」寻址

- **现象**(2026-10-25,接 `--profile-kind` 时):给 `real` 档案在簿记里写了个名字 `"default"`,

  Storage.getCookies 被拒绝:Failed to find browser context for id default
  ```
- **根因**:Chrome 的**默认 browser context 没有 id** —— `Target.getBrowserContexts` 也不列它,
  CDP 里只能用**省略 `browserContextId`** 来寻址它。给它编一个字符串名字,浏览器不认。
- **真机实测(Chromium 156,`probe-ctx.mjs`,`vps-jp`)**:

  | 命令 | 结果 |
  |---|---|
  | `Storage.getCookies {}` | ✅ `{"cookies":[]}`(落到默认 context) |
  | `Storage.getCookies {browserContextId:"default"}` | ❌ `Failed to find browser context for id default` |
  | `Target.createBrowserContext {disposeOnDetach:false}` | ✅ 返回真 id(如 `C9092D45…`) |
  | `Storage.getCookies {browserContextId:"<真 id>"}` | ✅ |
  | `Storage.getCookies {browserContextId:"nope-1234"}` | ❌ 同样失败 |

- **正解**:`real` 的簿记值取 `null` 表示「省略」——

  `persona`/`disposable` 走 `Target.createBrowserContext` 拿真 id,照常注入。
- **纪律**:凡是「把外部系统的隐式约定写成显式值」的地方,都要拿真环境验一次 ——
  单测里那个自造的 `"default"` 池子会**一直绿**,因为假对端是按我们的假设写的(这正是坑-31 的同族问题)。

## 坑-34 · 「没解析出来」被读成「没有这个特征」—— 假绿的第二种形状

- **现象**(2026-10-25 查 creepjs 那三轮时才看清):同一天的两次重跑,同一张页面,
  `pw-naive` 一次判 `passed`、一次判 `detected`,而两轮的 `headlessGrade` **完全相同**(`88`)。
  单看结论像"判据随机";看产物与提交历史才明白:**解析器与判据都换过代**(见下)。
- **根因**:旧解析用通用正则 **`\b([A-Za-z][A-Za-z]{3,30})\s*:\s*(true|false)\b`**(键取 `m[1].toLowerCase()`)。
  页面把名字与值挤在一起:
  ```
  × Like HeadlessnoChrome: truehasPermissionsBug: truenoPlugins: true...
  ```
  ⇒ 解出的是 `truenodownlinkmax` / `truehasheadlessworkerua` 这类**错键**(`pw-naive` 7 个、`ego` 8 个),
  一个都不在名单里;
  **同一轮还叠了第二个原因 —— 判据**:当时是「命中 tell 才 detected」外加 `grade ≥ 80 → passed`。
  换成 `a2ff8c6` 之后(逐个名字查子串 + **等级 ≥ 50 判 detected**)才有今天的结果。
  **两样都换了,而判据那一半是决定性的**:把旧读数原样喂给今天的判据就得 `detected`;只修解析器不换判据则仍是 `passed`。
  即:**「我没解析出来」被当成了「这项特征不存在」,而高分级又被当成了「不像 headless」。**
- **为什么这条危险**:它和坑-29(静默不启动)、「假对端绿」是**同一族** ——
  **失败模式长得像成功**。对检测类工具尤其致命:探针的失败会被读成目标的干净。
- **正解**:
  1. 解析**按已知名字逐个查子串**,不用通用词法切分(名字粘连时通用正则必错);
  2. **fail-closed**:等级**缺席**、且**一个名单内的名字都没出现** ⇒ 判 `error`,不许判 `passed`
     (`creepjs.py` 的 `_classify` 已加;用例落盘 `probe/tools/check_creepjs_classify.py`,13/13 通过);
     ⚠️ 代价照实记:等级在场时会盖掉为 true 的 tell —— 所以"tell 说了什么"在下游只能当辅证;
  3. 产物里带 `tellCount` 这类**计数**字段 —— 事后一眼就能看出"那一轮只解出 7 个键,而里面只有 3 个是真解析出来的"。
- **纪律**:凡是**从文本里抽取**再据此下结论的探针,都要问一句:
  **「抽不到」与「不存在」在这段代码里有没有被分开?** 没分开就是假绿。

## 坑-36 · `Runtime.evaluate` **需要 target session** —— 我们的自检 API 一直裸调,于是从来没跑成

- **现象**(2026-10-25):`probe/tools/webrtc_audit_via_ouuut.mjs` 第一次真跑,直接炸:
  ```
  CdpPipeError: Runtime.evaluate 被拒绝:'Runtime.evaluate' wasn't found
  ```
- **根因**:`Runtime.evaluate` **必须在某个 page 的 session 上发**;对着浏览器主通道裸发,浏览器答"没有这个方法"。
  而 `ouuut.auditWebrtc()` 原来的实现只有"有 sessionId 就带上、没有就裸发"两条路 ——
  从 CLI 脚本里调时**拿不到 sessionId**,于是这条路**必然失败**。
  这也解释了 HANDOFF 里挂了很久的那条「Not verified:auditWebrtc 真跑」——不是没空跑,是**跑不了**。
- **修法**:没给 `sessionId` 时**自己挂一个**:`Target.getTargets` → 取第一个 `page` → `Target.attachToTarget{flatten:true}`
  拿回 sessionId,再带着它 evaluate;并且把 evaluate 的失败**翻译成返回值**(`ok:false` + 可读原因),
  不再往上抛 —— 自检失败不等于通道坏了。
- **真机结果**(`--headless`,`Chrome/156.0.8078.47`):
  ```json
  {"ok":true,"counts":{"total":2,"public":0,"lan":0,"mdns":2,"loopback":0,"unknown":0},"leaks":[],"warnings":[]}
  ```
  ⇒ **公网候选 = 0**(ADR-014 的判据),两个候选都是 mDNS `.local`(缓解,不算泄漏)。
- **纪律**:凡是"我提供一个自检 API"的地方,都要有一次**从真实调用点**跑通的记录;
  单测覆盖了逻辑,不等于它在**真实调用上下文**里可用(与坑-28「从没被执行过的路径」同族)。

### 补记(同日,核验抓出来的一层):「跑通了」不等于「稳定跑通」

第一版修法只是"自己挂一个 page",核验分身拿同一条命令连跑 10 次:**3 次成功、7 次 `ok:false`**,报
`Execution context was destroyed`。根因是**启动竞态**:启动时那个 page 是 `chrome://newtab/`,
在它换 document 的窗口里 evaluate 就会炸 —— 无脑取 `pages[0]` 正好撞上。

- **修法两处**:① 挑页面时**优先 `https`/`file` 的真页面**,没有才退回内部页;
  ② 暂时性失败(`Execution context was destroyed` / `Cannot find context` / `wasn't found` / `Target closed`)
  **重试**(最多 4 次,250 ms 间隔),非暂时性(或调用方自己给的 sessionId 出错)当场收手。
- **再测**:同一条命令 **10/10 成功**(修前 3/10)。
- ⚠️ **还有一个会被读错的形状**:失败时返回 `counts` 全 0 + `leaks: []`,**外形上很像"公网候选 = 0"**。
  所以:JSDoc 与工具里都写死「**判据先看 `ok`**」,失败消息以「**未通过**」开头,工具在失败时给非零退出码
  并打印 `__VERDICT__ NOT_MEASURED`。
- **纪律**:「跑通一次」与「稳定跑通」是两件事;凡是结论依赖的读数,都要问一句**跑多少次、失败长什么样**。

## 坑-37 · 「省略某个参数」也是一种取值 —— 而无头的默认屏幕尺寸恰好是个指纹

- **现象**(2026-10-25):无头下我们**刻意不给任何窗口参数**,代码注释写的理由是
  「没有窗口可摆,给了只是噪音,还会让『桌面与服务器同一套参数』变得不成立」。
  真机一跑,检测站把这条直接点名:
  ```
  🟡 Screen is 800x600, the default screen size of headless Chrome (and of some virtual machines).
  ```
- **机制**:headless 没有真实显示器,`screen.*` 用默认 **800×600**。
  于是"什么都不给"不是"没有影响",而是**给了一个众所周知、可指纹化的常数**。
- **第二个坑(只修一半会以为修了)**:先加的 `--window-size=1920,1080` **没有效果** ——
  它改的是**窗口**,而 `screen.width/height` 依旧 800×600(实测:加完之后 warn 照旧)。
  真正定义"屏幕"的是 headless 自己的 **`--screen-info={1920x1080}`**
  (格式出自 Chromium 自己的文档与用例:`components/headless/screen_info/README.md` 与
  `headless/test/data/protocol/sanity/` 里的 `// META: --screen-info={800x600}`)。
  ⚠️ 顺带一条反直觉事实:`headless/public/switches.h` 对 `--window-size` 的注释说它
  *"also defines the headless screen size in lieu of --screen-info"*,但在 Windows + `--headless=new` 上**不成立** ——
  实测只给 `--window-size` 时 screen 仍是 800×600(上游注释在这一路径上不准)。
  **两个都给了**(`screen-info` 用 `x`、`window-size` 用 `,`);不过**消那 1 黄只需要前者**,
  `--window-size` 是产品取舍(见下)。
- **修法**:无头下 `--screen-info={1920x1080 isInternal=false workAreaBottom=48}` + `--window-size=1880,1000`。
  三条要点(第二条是核验者用突变测出来的):
  1. **只有 `--screen-info` 是"必需"的** —— 只给它(`16/0/0/16`)就能把那 1 黄消掉;
     `--window-size` 是**产品取舍**(窗口要是桌面尺寸、`viewport` 才像真人),不是消警告所必需。
     反过来,只给 `--window-size` **不行**(实测 3/3 仍是那 1 黄)。
  2. **窗口必须比屏幕小,而且屏幕要有任务栏** —— 第一版给的是"窗口 == 屏幕、`availHeight == screen.height`",
     于是 `screenX + outerWidth = 10 + 1920 = 1930 > availWidth 1920`(窗口探出屏外)、而且"没有任务栏",
     两处都是**自洽性破绽**(核验者直读 `window`/`screen` 抓到的)。现在:
     `outer 1880×1000 < screen 1920×1080`、`avail 1920×1032`(48px 任务栏)、`fitsW: true`、`taskbar: true`。
  3. **尺寸必须解析过再用** —— 第一版用 `String(size).split(",")` 取两段,于是
     `--window-size 1920` / `1920x1080` / `"1920, "` 都会拼出 `--screen-info={1920xundefined}`,
     而 **Chrome 不报错、悄悄退回 800×600** —— 正好把刚修好的那 1 黄带回来,且全程静默。
     现在先按 `^\d+,\d+$` 校验,不合法就退回默认值,并有专门的用例守这条。
- **结果**(真机,headless 与 headed 都是):`bot-detector` 16 项 **0 红 0 黄**;
  检测站自己的话 `headless → "No signs of headless Chrome"`、`viewport → pass`(无头下看到 **1852×899**,
  即 1880×1000 窗口的内区;有头走真实桌面,是 1707×825)。
- ⚠️ **别把它读成"像真实桌面"**:给的是**固定常数**(屏 1920×1080 + `dpr 1.0`(Chromium 默认)+ 24 位色深,
  每个实例都一样),而本机真桌面是 `1707×960 @ dpr 2.25`、`avail 1707×912`。换了更常见的常数,**常数还是常数**;
  真正的"按画像给自洽尺寸"要等 F5 的 seed 画像接进启动参数。
- **纪律**:① **「省略」是一种取值**,不是"没有影响" —— 默认值本身就是可被指纹化的;
  ② 同一个概念在 Chrome 里常有两个开关(窗口 vs 屏幕),**只改一个会得到"看起来改了但没变"**;
  ③ 凡是"我们刻意不给某参数"的地方,都该在真机上验一次**那个默认值长什么样**;
  ④ **改完要量几何自洽**:`window` / `screen` / `avail` / `screenX` 之间是能算出矛盾的
  (`screenX + outerWidth > availWidth` 这种),只看"警告没了"会漏掉它。

## 坑-38 · 长驻脚本里 `console.*` **不落地** —— 而我先给出了两个错的机制

- **背景**(2026-10-25):要给探针加一个走**我们自己 CLI** 的 target(`probe/targets/ouuut.py`)。
  我们的 CLI 是"一次一进程、进程结束浏览器就关",所以**不能**照 ego 那种"每个操作跑一次 CLI"的写法
  (那样每次都是全新浏览器,页面状态接不上)。于是设计成:起**一个长驻 CLI 进程** + 一套行协议。

- **现象**:第一版(命令走 stdin、结果读 `stdout=PIPE`)→ 探针**一声不响地挂住**:
  输出目录建了就空着,`run.py` 停在 `run × ouuut × bot-detector ...`,**没有任何报错**。

- **真正的机制(在仓库里,不是猜)**:harness 的 **output sink 把 `console.*` 缓冲起来,
  只在脚本跑完(或进程 exit)时 flush** ——
  `harness/package/ego-browser/dist/src/run.js:59,82`(`execute()` 开头 `resetSink()`,
  脚本跑完 `flushSink(stdout, false)`;出错时 `flushSink(stdout, true)`),
  配套 `dist/src/output-sink.js`(`bufferOutput` 攒缓冲、`createRoundConsole` 往缓冲写、
  `installLifecycleFlush` 只挂 `beforeExit`/`exit`)。
  ⇒ **长驻脚本的 `console.*` 永远不会在会话期间出现**,与 stdout 是管道还是文件**无关**。
  要实时,得绕开它:`fs.writeSync(1, ...)` 或直接 `fs.appendFileSync(结果文件, ...)`
  (核验实测:`console.log` 首行 6.70 秒才可见 = 脚本结束那一刻;`fs.writeSync(1, …)` 首行 **0.66 秒**)。

- **我先后给出的两个错机制(照实记,这是本文最该被读的部分)**:
  1. 「stderr 管道没人读、写满 64 KB 就死锁」—— 改成合并流后**照样挂**;
  2. 「长驻子进程 + Python 的 `stdout=PIPE` 收不到输出,改成文件就有」—— 核验做了对照:
     **把 stdout 重定向到文件,运行期照样 0 行**(8 秒),只有脚本结束后才有内容;
     而**同一个 PIPE** 换成 `fs.writeSync(1, …)` 就能实时收到。
     ⇒ **stdout 的去向根本不是判别变量**,我那次"判别性实验"判错了东西。

- **另一条(这次是对的,但要收窄)**:脚本**从 stdin 读**时,CLI 必须把 stdin 读到 **EOF** 才会开工
  (命令早早写进管道、但管道保持打开 → 回复要等到关闭才来;`< 文件` 立刻回)。
  ⚠️ **但它只对 stdin 那条路成立**:走 `--script <file>` 时**根本不碰 stdin**,
  核验实测"stdin 管道一直开着、一个字节不喂"→ 0.19 秒就开工、正常退 0。
  (我先前把这条外推成"哪怕用 `--script` 也一样" —— **那是错的**。)

- **正解(现在的成品)**:命令与结果**都走文件** —— 驱动轮询 `cmds.jsonl`、用 `appendFileSync` 写 `res.jsonl`
  (绕开 output sink,实时);`stdin=DEVNULL`,`stdout/stderr` 落日志文件;Python 侧按 offset 轮询 +
  **每次调用都有超时上限**(超时杀 CLI 并把日志尾部带上,别让挂住伪装成沉默)。

- **纪律**:
  1. 给长驻子进程写**任何**协议之前,先用最小实验确认那一层通不通 —— **别在完整适配器里 debug 传输层**;
  2. **判别性实验要真的只差一个变量**:我那次差了两个(去向 + 读法),于是把"缓冲"读成了"管道问题";
  3. 机制要**回到源码里找**,别停在"现象看着像……"。这次找到答案只花了一次 grep(`flushSink`)。

## 坑-39 · 杀 CLI **不等于**收尾 —— 会话目录一定会留下,进程树**多半会**自己走

- **现场**(2026-10-25):给探针适配器加了"超时就杀掉 CLI"之后,`%TEMP%` 里开始出现
  **删不掉的** `ouuut-session-<pid>` 目录(`EBUSY`)。查进程列表时,那一次的 CLI(node)**早就没了**,
  但**十三个浏览器进程还活着** —— 主进程、crashpad-handler、gpu-process、两个 utility、五个 renderer。

- **根因**:浏览器是 CLI spawn 出来的**子进程**。CLI 一被 `kill`,它收尾那条路
  (关浏览器 → 删会话临时档案目录)**根本不会执行**。于是磁盘上那个档案目录没人清。

- ⚠️ **核验复核后的更正(重要,别照我原来的说法传)**:
  * **可靠复现的只有"目录留下"** —— 裸 kill CLI 之后,目录一直躺在 `%TEMP%` 里直到手删;
  * 我那次看到的「13 个进程还活着」**没能复现**:核验造了三次旧现场(空闲驱动裸 kill / 超时路径裸 kill /
    长驻驱动裸 kill),浏览器都在 **≤0.3 秒内自行退出**(CDP 管道断了)—— 所以"每超时一次就多留一棵树"
    这个说法**站不住**,应改成「**多半会自己走,但不能指望**」;
  * 「第一次 `rmtree` 会 EBUSY」也没复现(核验每次都第一次成功)—— 保留重试只是为了稳,
    不是因为已经证到必然失败。

- **正解**(适配器 `probe/targets/ouuut.py`):
  1. `_kill_tree()`:Windows `taskkill /F /T /PID <pid>`、POSIX `os.killpg(os.getpgid(pid), SIGKILL)` ——
     **不去指望子进程自己发现父进程没了**;
  2. `_cleanup_session_dir()`:清掉 `<tmp>/ouuut-session-<cli pid>`,**带重试**(6 次 × 300 ms);
  3. 三条路径都走它们:超时、`close()` 的非常规路径、以及"CLI 中途自己退出"那条。
  4. ⚠️ **POSIX 上必须 `start_new_session=True`**(见下条):否则子进程继承我们的进程组,
     `killpg` 会把**探针自己**一起 SIGKILL(`contextlib.suppress` 拦不住 SIGKILL)——
     这是核验抓出来的 P1,Windows 分支不受影响。

- **纪律**:凡是"杀一个进程来表示放弃/超时"的地方,都要问一句
  **「它有没有子进程,那些子进程谁来收」**;另外,**一次观测不等于可复现的规律** ——
  我把自己看到的一次(13 个进程)写成了"每超时一次就多留一棵树",核验三次都没复现。

## 坑-40 · 参数"配对了"不等于"作用在东西上" —— 我把代理绑给了一个永远没有页面的 context

- **背景**(2026-10-25):实现 F13「按档案绑代理」。查源码发现 `Target.createBrowserContext` 支持
  `proxyServer` / `proxyBypassList`(Chromium 156),于是按 kind 分流:
  `persona` / `disposable` 的出口交给 **context 级**代理,浏览器级 `--proxy-server` 就不给了。

- **看起来全对**:参数真的发给了浏览器(假对端能看到 `proxyServer`)、
  用"死代理"建 context 时那个 context 里的页面**确实**加载失败 ⇒ **context 级代理机制成立**。

- **错在哪**:CLI/harness 建页走的是 `Target.createTarget`,而它**不带 `browserContextId`** ——
  于是页面**永远落在默认 context**,那个绑了代理的 persona context **一生没有一个页面**。
  结果:`--profile-kind persona --proxy <真代理>` **整场会话静默走直连**(实测出口 IP 等于本机直连 IP),
  而且**零告警**:既没有浏览器级出口、context 级出口也照不到东西。

- **怎么发现的(这条最值得抄)**:不是看代码看出来的,是**用"死代理"当探针**:
  绑一个不存在的代理(`socks5://127.0.0.2:9`),如果页面还能打开 ⇒ 说明**这条路根本没被走**。
  修完后同一个死代理 ⇒ `net::ERR_PROXY_CONNECTION_FAILED` ✓(证明页面真的在带代理的 context 里);
  再用真代理对比出口 IP:直连 `124.211.130.95`、代理 `129.225.148.47` ✓。

- **正解**:`createTab` 带上会话档案的 `browserContextId`
  (`archive.browserContextFor(profileId)`;`real` 是 `null` ⇒ 省略参数 = 默认 context,这是 Chrome 的寻址方式)。
  一条用例守两个方向:有 context id ⇒ 必须带;`real` ⇒ 必须**不**带(带了会被 Chrome 拒)。

- **纪律**:
  1. 加任何一个**改流量路径**的开关(代理、出口、隧道)之后,必须验证**流量真的走了那条路** ——
     "配置生效了"和"东西用上了"是两件事;
  2. 最便宜的路由探针是**故意让它必然失败**(死代理/黑洞地址):还能通 ⇒ 这条路没被走;
  3. 凡是"我给 A 绑了东西,但 B 才是实际用东西的那个"这类接线,**默认怀疑自己绑错了对象**。

## 坑-41 · 写「实测」却不落盘 = 没法复核 —— 同一条注释前后给出相反结论

- **触发**(2026-10-25,核验指出):`native/binding/proxy.mjs` 的兜底注释写着
  「Chromium 156 实测**不收**带凭据的代理串(`ERR_NO_SUPPORTED_PROXIES`)」,
  但**全仓查不到任何证据**(`grep -rn ERR_NO_SUPPORTED_PROXIES` → 唯一命中就是那条注释本身);
  而**父提交在同一个位置**写的是相反的「实测这种形状的代理确实会生效」。
  两次都只有"实测"两个字,没有命令、没有输出 ⇒ 后人无法判断该信哪句,只能把两句一起怀疑。

- **这次落盘的可复核实测**(命令 + 输出都在这):
  ```
  # 对照组:同样的代理,只是不带凭据 —— 必须先让这条通,证明"只改了一个变量"
  node native/bin/ouuut.mjs nodejs --script <出口IP脚本> --headless --proxy socks5://198.51.100.7:41105
      => 出口 129.225.148.47                       # 代理生效
  node ... --headless --proxy socks5://u:p@198.51.100.7:41105
      => net::ERR_NO_SUPPORTED_PROXIES             # 带凭据 -> 浏览器直接不收
  # context 级那条路(--profile-kind persona)重跑同样两步:
      => 无凭据 出口 129.225.148.47 / 带凭据 net::ERR_NO_SUPPORTED_PROXIES
  # 排除干扰:无代理时 http://example.com 正常打开(所以不是 http 或网络的事)
  ```
  ⇒ **带凭据的代理串 Chromium 一律不收,浏览器级与 context 级两条路都一样。**

- **所以**:凭据脱敏**仍然必须**(那串会被原样拼进 `--proxy-server=...` 并进诊断/错误消息),
  但理由**不是**"这种代理能用" —— 见 `proxy.mjs` 里那三行注释。

- **教训**:写「实测」二字时,同一条注释里带上**命令与输出**(或指到本文)。否则"实测"只是另一种猜测,
  而且比普通猜测更坏 —— 它会让下一个人**停止怀疑**。

- **同一条坑里的第二、三处**(2026-10-25 核验的下一轮,两个都是**漏抹**,比误伤严重):
  - **口令含 `@`**:正则只吃到**第一个** `@`。`socks5://u:p@ss@h:1` → `socks5://***@ss@h:1`,口令尾巴 `ss` 留在诊断里。
    这不是"语法外的怪例" —— `parseProxy` **自己认可**这种形状:`parseProxy("socks5://u:p@ss@h:1")`
    实测返回 `{host:"h", port:1, hasCredentials:true}`(WHATWG 以**最后**一个 `@` 为分隔),
    也就是说用户把 `p@ssw0rd` 当口令打是**正常输入**。

- **教训(变异只绿 = 那多半是死代码,不是"用例写少了")**:核验删掉盘符前瞻 `(?![A-Za-z]:[\\/])` 时**全套仍绿** ——
  并给出构造性证明:那时尾段禁反斜杠,推导下来前瞻永远不改变匹配。**这说明前瞻当时是死代码。**
  修法是让前瞻**真的挡事**(尾段放宽后它就是**唯一的**路径挡板),再补用例让它删掉就红 ——
  现在删前瞻,"别误伤 Windows 路径"那条**会红** ✓。

- **第三段:正则这条路本身走不到底(2026-10-25 第三轮 fuzz 核验)**。核验自写 5200 条生成式代理串,
  **29.6% 抹不净**,归因四类:口令含空白 832、口令含 `/` 392、用户名含 `@` 310、前瞻误吞 `u:\` 4

  - **根因**:`redactProxy(text)` 面对的是**任意自由文本**(stderr、错误消息),它**不知道边界在哪** ——

## 坑-42 · 缺省字段填 `null` 还是 `undefined` —— 这是**接缝契约**,不是风格问题

- **现象**(2026-10-25):harness 的 `await page.snapshot()` 在我们这套上**从来跑不通**:
  抛 `Invalid persisted Page refs; take a new snapshot`(`page-ref-registry.js` 的 `validatePageRefState`)。
  而原生自己的 `ouuut.snapshot()` 一切正常 —— 所以此前没人发现。

- **两层**:
  1. 原生把 `refs` 当**对象映射**返回,而 harness 的 `compactSnapshotResult` 按**数组**迭代(`for (const ref of result.refs || [])`)
     ⇒ `TypeError: object is not iterable`。**已修**:`snapshot.mjs` / `oopif.mjs` 统一返回数组(每条仍是 §4.2 形状、含 `refId`)。
  2. 修完第一层,又撞上第二层:harness 的 `validatePageRefState()` 要求每个 ref 的
     `frameId / documentId / role / name` 是 **`string | undefined`** —— **`null` 直接判整份 refs 非法**。
     我们原来的记录写的是 `frameId: frameId ?? null`、`role: role ?? null`、`name: name ?? null`。

- **实证**(拿 vendored harness 代码直接喂):
  ```
  refs 里 frameId/role/name 填 null      -> restore() 抛 Invalid persisted Page refs
  refs 里同样字段「省略」(undefined)      -> restore() 通过
  ```
  也就是说:**「没有这个值」在接缝上必须表示成"键不存在/undefined",不能表示成 `null`**。

- **修法**:`snapshot-refs.mjs` 里缺省字段**不再写进记录**(`if (v !== null && v !== undefined) record.k = v;`)。
  顺带把这条契约写成**用例**:`snapshot-refs.test.mjs` 把原生产出的 refs 真的喂进 harness 的
  `merge -> exportState -> restore` 与 `validatePageRefState`;把 `?? null` 改回去,这条用例会**红**。

- **教训**:
  1. **接缝上的"空值表示法"是契约**,写之前去对接方代码里看它接受什么(这里 `string | undefined` 接受,`null` 不接受);
     类型看起来"都是空",在对端眼里一个是合法一个是非法。
  2. 「原生 API 能用」不等于「接缝上的那条路能用」:两条路吃的是同一份数据,但**消费方式不同**(数组 vs 映射、undefined vs null)。
     验收要打**对端那条路**(`p.snapshot()`),别只打自己那条。


## 坑-43 · 服务端这两个 bug 都是"写用例/真机跑"才露出来的

**背景**(2026-10-25,做 P5 三入口):HTTP/WS 与 MCP 两个入口写完后,自己写的用例立刻抓到两条 bug,
两条都不是"逻辑写错",而是**这类代码特有的形**:

1. **响应顺序**:MCP 的 `JSON.parse` 原本放在串行队列**外面**,解析失败就立刻同步写一个 `-32700` ——
   于是坏行会**插到**前面那条请求的响应之前。响应顺序 ≠ 到达顺序。按 id 配对不会错位,但顺序**本身是协议的一部分**,
   而且这种"一部分走队列、一部分不走"的写法迟早会咬人。
   ⇒ 修法:解析失败也**进队列**(所有写出都经过同一条链)。
2. **关服务卡死**:`server.close()` **不跟踪升级过的 socket**,`closeAllConnections()` 也**不会**碰它们 ——
   结果是"关服务"永远等不到回调、进程不退出(实测:`node --test` 那个文件直接挂到超时)。
   ⇒ 修法:升级成功后把 socket **自己记账**,关服务时逐个 `destroy()`。

**教训**:网络服务的正确性一半在"字节怎么排、连接什么时候真的关"这类地方。
这两条都很适合**写用例**,而且写起来很便宜(假 core + 真 socket 即可)——
不写用例的话,它们的表现分别是"偶尔对面报解析错"和"偶尔 CI 挂到超时",都是那种查一天也不一定查到的现象。

## 坑-44 · "同一个东西"可能有两套渲染 —— 还有一条硬编码的全局名

**背景**(2026-10-25,P5 验收要求"同一段任务经三条入口驱动,快照文本一致")。

- **第一层**:我第一版服务端直接调**原生** `api.snapshot()`。它返回的是**对象** `{content, refs}`,
  而"变成给人读的一行行文本"是 **harness 的页面模型**干的活(`compactSnapshotResult` 那条)。
  于是同一页面在 CLI 与 MCP 下拿到的**不是同一样东西**:一侧是化简后的行,一侧是缩进树。
  ⇒ 服务端也装 harness 的 SDK(`installEgoSdk`),三入口走同一条管道。
  **教训**:当验收写着"结果一致"时,先问**"这个结果是谁渲染的"** —— 渲染层不同,一致就无从谈起。
- **第二层**:`api.snapshot()` 的形状有两种(字符串 / 对象)。`String(obj)` 会得到 `"[object Object]"`,
  而且它在日志里看起来"有内容"(不是空),最容易被当成"页面没加载"。
  ⇒ 形状不确定的返回值,吐出前**显式判定**,别靠 `String()`。
- **第三层(顺带抓到的真 bug)**:随包的 harness **硬编码**读 `globalThis.ouuut`(`dist/src/helpers.js`),
  它不认识别的名字。所以 `--namespace foo` 会让脚本里的 `taskSpace()` 落到 harness 自己的替补实现上,
  报一句 `listTaskSpaces requires ego.listTaskSpaces` —— 错误信息**完全指不到自定义命名空间**。
  ⇒ 我们**两个名字都装**(`ouuut` 给 harness、`<name>` 给脚本),并在 `--help` 里写明这个语义。

## 坑-45 · 守卫按**名字**归类,把整条动作路径堵死了 —— 「能看快照、点不动任何东西」

- **怎么发现的**(2026-10-25,写 P9 的 shadow DOM 探针时):探针里有一条**对照**:先点一个**光 DOM** 的按钮,
  确认"点击"这条路本身是通的,再去看 shadow 里的按钮。结果**对照就红了** ——
  而且报错内容不是"点不到",是一串 CDP 消息的回显:`Page.setInterceptFileChooserDialog ...`。

- **根因**:我们自己的 CDP 守卫(`native/binding/cdp-guard.mjs`)把这条方法按**名字**归进了"页面注入类"
  (`pwInitScripts` / `documentInterception` 那类)并 **HOLD**;而 harness 的**每一个动作**
  (`click` / `fill` / `press` / `type`)都会**先发它** ⇒ **所有动作被自己的守卫拦死**。
  快照照旧能用,所以表面看不出问题 —— 直到有人真的去点。

- **判断错在哪**:它和 `Page.addScriptToEvaluateOnNewDocument` / `Page.setBypassCSP` / `Page.setDocumentContent`
  **不是一类**:那三条会往页面里注入东西(脚本 / 策略 / 文档内容),而这条只是让浏览器把"文件选择对话框"
  交给调用方 —— 既不注入脚本、也不留页面绑定。归类靠的是名字像不像,不是行为像不像。

- **修法(移进 `KNOWN_SAFE`,并把依据写成可复核的两条)**:
  1. 动作恢复:探针的对照组从红变绿(shadow 里、slot 投影的按钮也都点得动);
  2. **检测站读数不变**:同一探针跑 `bot-detector`,仍是 **16 pass / 0 红 0 黄**(和我们放行前一致)。
  ⇒ 结论是"放行它不会让检测面变脏",而不是"应该没事"。

- **教训**:
  1. **分类按事实,不按名字。** 一条 HOLD 规则的代价不一定是"少一个功能",可能是**整条产品路径不可用**。
  2. **动作路径必须真机冒烟。** 我们的用例此前覆盖了快照与守卫本身,却没有一条"点下去真的生效" ——
     于是这个洞要靠"顺手做的对照"才发现。凡是产品承诺"能操作"的地方,都要有一条**真的去操作**的证据。
     (同一类:shadow DOM 的可见性也必须真造一个 shadow root 去看,不能靠读代码猜。)
  3. 顺带记个**取舍**:放行之后,文件选择对话框**不再被拦**(harness 拿它做文件上传)。
     要恢复上传能力,得让守卫**改写**这条命令(传 `enabled: false` 不行/行,得单独定),别再把整条路拦死。
  4. 同一天还顺手修了一条**偶发红的用例**(等固定 150 ms 不够,整套并发跑时会红)——
     偶发红比没有用例更坏:它会让人开始忽略红色。固定等待一律换成**有上限的轮询**。

## 坑-46 · 「零遥测」不是一个开关,是一份**清单** —— 我们量出来了,它**不是零**

- **背景**(2026-10-25,做 P9):计划的原话是"断网跑核心链路 + `pktmon` 抓包确认零第三方上报"。
- **换了个更合适的仪器**(不需要管理员权限、还能看见**主机名**):写一个
  **记录式 SOCKS5**(`probe/tools/egress_watch_socks5.mjs`)—— 它**全部拒绝转发**
  (回 `connection refused`),所以**本机零出网**;同时把每一次 `CONNECT host:port` 记下来。
  再把浏览器用 `--proxy` 指过去,跑一段**只用本地页**的核心链路(`about:blank` + 页面内造 DOM)。
- **两个结果**:
  1. ✅ **无出网下核心链路全可用**:建页 / 快照 / **点击** / 取值都正常;
     而访问公网地址**必然失败**(`ERR_SOCKS_CONNECTION_FAILED`)—— 这一条是清单可信的前提:
     它证明代理**确实生效**,所以"清单很短/很长"都不是因为流量绕过了仪器。
  2. 🔴 **浏览器启动时仍然去连了四个 Google 域**(实测顺序):
     `clients2.google.com:80`(变体种子)、`accounts.google.com:443`(登录)、
     `www.google.com:443`、`update.googleapis.com:443/80`(组件更新,多次)。
- **试过、并且**量到**无效**(所以**没有**留在代码里):`--disable-component-update`、
  `--disable-component-extensions-with-background-pages`、`--disable-domain-reliability`、
  `--disable-client-side-phishing-detection`、`--metrics-recording-only` ——
  一台主机都没少(而 `--disable-background-networking` / `--disable-sync` 本来就在参数里)。
  加开关是**单变量**实验:加之前量一次、加之后再量一次,读数不变 ⇒ 撤回,不留 dead weight。
- **结论(不冒充)**:「零遥测」**目前没有做到**。要真做,只有两条路:
  在**出口层**拦(DNS/防火墙/代理的拒绝清单),或者在 **features 层**逐项关 ——
  后者每个开关都要过"**检测站读数不变**"这一关(我们已经有这条判据,见坑-45 的做法)。
  仪器已经建好(`probe/tools/zero_telemetry_via_ouuut.mjs`),任何后续改动都能**两秒复测**。
- **追加(2026-10-26,找到能用的杠杆了)**:上面五个开关都没用,但**解析层**有用 ——
  `--host-resolver-rules=MAP <host> ~NOTFOUND` 把那四个域名映射成"查不到":
  实测(探针 `probe/tools/phone_home_blocked_via_ouuut.mjs`,直接导航那四个域名)
  **四个全部 `ERR_NAME_NOT_RESOLVED`**(连 DNS 都不查,更谈不上出网);
  而**检测站读数不变**(16 pass / 0 红 0 黄)。
  - **默认开**,并给了出口:`--allow-phone-home`(显式导航这几个域名确实要访问的人才给)。
  - ⚠️ **只覆盖直连那条路**:Chrome 的 `socks5://` **本身就是远端解析**(域名交给代理去解),
    所以走代理时这条规则**不生效**(记录式出口里照样能看到那四个 CONNECT)——
    那种情况下的拦截点在**代理侧的拒绝清单**。这一点是"零遥测"目前**没有完全做到**的原因。
  - 教训(补):**先找对层**。同样的目标,加 5 个功能开关一个主机都没少;换到解析层一行就干净利落 ——
    前面那 5 个开关不是"写得不对",而是**拦在错误的层**上。

- **教训**:
  1. 「零 X」必须有一份**可读的清单** —— 否则"零"和"没测"在报告里长得一模一样。
  2. **加开关要量。** 这次我一次加了五个"听起来该有用"的开关,量完发现一个主机都没少。
     如果不量,它们会永远躺在参数表里,并让后来人以为"回连已经被关掉了"。
  3. 仪器要选**拒绝式**的:既证明"没有字节出去",又拿到"想连谁"的清单 —— 比抓包更适合回答这个问题。

- **第二次追加(2026-10-26,走代理那条也补上了)**:解析层对 `socks5://` 不生效(远端解析),
  于是做了一道**出口闸**(`native/binding/egress-guard.mjs`):一个**本地 SOCKS5**,
  浏览器先连它,命中回连名单就**当场拒**(不查 DNS、不出网),其余转发给真上游(上游可以是另一个 SOCKS5,也可以直连)。
  - 接线:`openSession()` 里"有 `--proxy` 且没给 `--allow-phone-home`"就起闸,并把浏览器的代理**改写成闸的地址**。
  - **踩到的坑(值得记)**:第一版我在 `openSession` 里改写 `opts.proxy`,但 CLI 已经把
    `buildBrowserArgs()` 的结果**先算好**传进来了 ⇒ 改写等于没改(浏览器照样直连上游)。
    ⇒ 改成把 `buildArgs` **函数**传进 `openSession`,**在决定闸之后**才算启动参数。
    (教训:**"改写配置"和"生成产物"的先后顺序**,也是一种契约。)
  - **实测**:同一个记录式出口,走代理跑一次 —— 尝试的目标从 5 个(四个域名 + 我们的端点)降到
    **只剩 `api.ipify.org`** ⇒ PASS。也就是说**走代理时回连也出不去了**。
  - 边界仍写明:闸只管 **TCP CONNECT**;上游不是 socks5 时闸自动跳过并打一行说明(不静默失效)。

- **教训(补)**:**先找对层**。 · 双档案双出口:CLI 那条路通了,**服务端那条路走不通** —— 边界要写清楚

- **背景**(2026-10-26,做 P5 的尾巴):一个会话里要放**两个档案**(各自绑不同出口),页面按档案落 context。
  接线点只有一个:我们的 `createTab()` —— harness 的 `page-model` 调 `ego.createTab(url)` 时**只给 url**
  (它的 dist 里**从不出现** `browserContextId`),所以"这张页属于哪个档案"只能由**当前选中的任务空间**决定。
- **改动**:`createTaskSpace(name, profileId)` 现在会把空间绑到档案上(`archive.bindTaskSpace` —— 这是它**第一个**生产调用方),
  `createTab` 按「显式入参 > 当前空间的档案 > 会话主档案」选 context;CLI 新增 `--profiles '<json>'`
  (一个会话开多个档案,各自带 proxy)。
- **实测(值得记下来的形态)**:两条**必须**同时满足,否则报错都很难懂:
  1. **空间要在开页之前建好** —— harness 建空间时要求浏览器**恰好一个标签页**,
     一旦开过页再建新空间就是 `new task space expected one default tab, found 2`;
  2. `taskSpace(name, { profileId })` **是对象签名**(不是位置参数),而且**对已存在的空间再带 profileId 会抛**
     (`profileId only applies when creating a new task space`)。
  按这两条写,CLI 那条路**通了**:一个会话、两个档案,出口分别 `129.225.148.47`(JP 代理)与
  `124.211.130.95`(直连)—— 见 `tools/verify-dual-profile.mjs`(可复跑)。
- **服务端那条路:不通,而且不装**。HTTP/MCP 要先起服务、再按请求开页,而"建空间"必须在开页之前 ⇒ 时间顺序对不上;
  我试过**预建所有空间**(可行)+ 每请求 `useTaskSpace` 选中 ⇒ 快照开始认错文档
  (`Page changed during snapshot`);换 harness 自己的 `switchTaskSpace` 也没修好。
  ⇒ **决定**:服务端**只服务一个档案**;给了 `--profiles` 就**明确拒绝**并指路 CLI
  (错误码 `OUUUT_SERVE_NO_MULTI_PROFILE`)。**不做半可用功能** —— 一个"有时能用"的多档案参数,
  比一个明说"这条入口不支持"的边界,**更贵**。
- **教训**:
  1. 上游(vendored)组件的**状态模型**是硬约束:能改的只有我们自己那层。碰不动时,**把边界写进错误信息**,
     而不是把功能做成"大部分时候能用"。
  2. 一个功能在一条入口通了、另一条不通时,**验收脚本要把两边都写进去**:
     一条断言"能用",另一条断言"明确拒绝"。否则半年后没人知道第二条是**故意**的。
  3. `bindTaskSpace` 这种"写好了却没人调"的 API,等于**没有防线** —— 接上生产调用方之后,它才真的开始工作。


## 坑-48 · `vps-jp-gitea` 是 **git-shell**,跑不了命令 —— 要 shell 用 `vps-jp`

- **现象**(2026-10-26,做 P7 时想上远端起静态服务):`ssh vps-jp-gitea 'echo OK'` 回一句
  `error: Invalid repository path` —— 那是 gitea 的 SSH 入口(用户 `git`、端口 2222),被限制成只能用 git 协议。
- **修法**:`~/.ssh/config` 里另有一个 **`vps-jp`**(同一个 `HostName`,用户 `ubuntu`)——
  那才是能跑命令的 shell 入口。两台其实是**同一台机器**(tailnet 名 `<主机名>.tailnet.invalid`)。
- **教训**:同一个主机名在配置里出现两次(不同用户/端口)时,**别名才是"身份"** ——
  `vps-jp-gitea` = "git 远端",`vps-jp` = "这台机器的 shell"。搞错别名时错误信息完全指不到重点
  (`Invalid repository path` 不会提示你"你用了 git 入口")。

## 坑-49 · 池规格文件被租约表**覆盖**(第一次 assign 就把规格写没了)

- **现象**:`--proxy-pool pool.json` 第一次分配之后,`pool.json` 变成了租约内容 —— 下次启动直接报规格不合法。
- **根因**:`openPool({file})` 只写了一个 `file`,`storeFile = file` ⇒ 「从文件读规格」与「把租约写回文件」
  顶上了同一个路径。**规格是只读输入,租约是可写状态,两者不该共用一个文件。**
- **修法**:调用方给了 `spec` ⇒ `file` 就是租约表;规格是**从** `file` 读的 ⇒ 租约表 = `file + ".leases.json"`。
  回归用例:`规格文件不许被租约表覆盖`。
- **一般教训**:凡是「读某个文件当配置」的功能,先问一句「我会不会写同一个路径」。
- **位置**:`native/binding/rotation.mjs` · 2026-10-26。

## 坑-50 · 探针里量出口:别借 harness 的任务空间模型,直接用 `runtime.probeEgressIp`

- **现象**:探针想「两个档案各量一次出口」,用 harness 的 `taskSpace(name, {profileId})` 建**第二个**空间时炸:
  `new task space expected one default tab, found 2`;而关空间用的 `closeTaskSpace` 在脚本里**根本没定义**。
- **根因**:harness 的任务空间模型假设「一次一个空间 + 一个新空间恰好一个默认页」,它不服务
  「一个会话里两个空间同时在」。**这不是我们代码的 bug**(三入口与双档案接线都正常),是**探针不该借那个模型**。
- **修法**:量出口用**产品自己的仪表** —— `await ouuut.createTaskSpace(name, profileId)` 之后
  `await ouuut.probeEgressIp()`:它复用 `createTab`(页面落在**当前档案**的 context 里)、量完自己把自检页收掉。
- **顺带**:`--profile-id` **不是** CLI 开关 —— persona 不给 id 时用 kind 当 id,所以钉子的键是 `persona`。
- **位置**:`probe/tools/pool_leases_via_ouuut.mjs` · 2026-10-26。
