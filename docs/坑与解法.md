## 坑-1 · `bash` 指向 WSL 启动器

- **现象**:`i/o error: stream did not contain valid UTF-8`;或直接吐出 WSL 的
  「适用于 Linux 的 Windows 子系统没有已安装的分发」中文提示(乱码);
  同时 `chmod` 等命令报 `command not found`
- **根因**:系统 PATH 里的 `bash` 解析到 WSL 的启动器,不是 Git Bash
- **正解**:显式调用 `"C:/Program Files/Git/bin/bash.exe"`
- **复现记录(2026-10-24)**:同一个会话里,**前面多次 `bash` 调用走的是 Git Bash,
  中途突然变成 WSL** —— 说明这不是「装没装对」的静态问题,而是**每次调用都可能不同**。
  凡是**脚本语法检查 / 需要 chmod / 需要 Unix 语义**的调用,**一律写全路径**:
  ```bash
  B="C:/Program Files/Git/bin/bash.exe"
  "$B" -c 'bash -n tools/20-rebase.sh && echo OK'
  ```
  这样即使外层 shell 变了也不受影响。已被 `tools/20-rebase.sh --dry-run` 的冒烟测试验证。

## 坑-5 · `secrets_manager.py read` 的两个陷阱

- **陷阱 1:两个命令返回结构不同**
  - `read <service>` → `{"service", "num_keys", "keys": {...}}`
  - `read <service> <key>` → `{"service", "key", "value"}`
- **陷阱 2:`read <service>` 里的 value 是【打码】的**
  - 整服务读出的值形如 `http...7081` / `b602...1a53`(定长 11 字符),**不是真值**
  - 照着它去请求 → `ValueError: unknown url type: 'http...7081/api/v1/user'`
- **正解**:要真值一律 `read <service> <key>` 然后取 `['value']`;
  整服务读只用来**列 key 名**

## 坑-10 · Playwright `ignore_default_args=True` 会让浏览器起不来

- **现象**:
  - `ignore_default_args=True` + `channel="chromium"` → `TargetClosedError: Target page,
    context or browser has been closed`(日志显示 `<launched> pid=...` 后立刻 graceful close)
  - `ignore_default_args=True` 不加 channel → `Timeout 20000ms exceeded`(headless-shell
    起来了但 Playwright 连不上)
- **根因**:`True` 会把 Playwright 自己**运行所必需**的开关一起丢掉(含 `--headless` 之类),
  不是「只丢它列在文档里的那些」
- **正解**:给**具体名单**,只丢你确实不想要的:
  ```python
  ignore_default_args=["--disable-ipc-flooding-protection",
                       "--disable-popup-blocking",
                       "--enable-unsafe-swiftshader"]
  ```
  `--remote-debugging-pipe` 是**独立追加**的,不受此项影响,所以连接本身没问题
- **同时**:`channel="chromium"` 才会用完整 Chromium(默认走的是 `chrome-headless-shell`,
  UA 里写 `HeadlessChrome` 且没有 `window.chrome`)

## 坑-13 · JS 正则 `\S` 吃不掉 emoji(代理对)

- **现象**:`bot-detector` 探针里 `td.innerText.match(/^(\S)\s+(.*)$/)` 对 `"⚪️ dummyFn"` 成功,
  但对 `"🔴 runtimeEnableLeak"` 失败 —— 结果 `mark` 为空、整个 emoji 留在 `name` 里,
  12 项测试全被归为 `unknown`,整条结果 `error`
- **根因**:`⚪`(U+26AA)是**单个 UTF-16 码元**;而 `🔴`(U+1F534)是**代理对**。
  正则不带 `u` 标志时 `\S` 只匹配一个码元 = 高代理项,后面接的不是空白 → 匹配失败
- **正解**:别用正则取 emoji。按第一个空格硬切:
  ```js
  const sp = s.indexOf(' ');
  const mark = sp < 0 ? '' : s.slice(0, sp);
  const name = sp < 0 ? s : s.slice(sp + 1).trim();
  ```
  Python 侧再 `str.replace("\ufe0f", "")` 去变体选择符
- **教训**:**先看原始证据再下结论** —— 这一轮 5 个 target 全部 `error`,
  若不看 `detail.tests` 就会误判成「浏览器起不来」

### 附:同一类错误还有第二个版本 —— 用文本正则判成败

- **现象**:`bot-detector` 探针的第一版用关键词正则判「失败」,
  正则会命中 `patchright` 那一行的 **`"No leak detected."`** 里的 `detected` →
  把一个**通过**判成**失败**
- **正解**:**优先解析结构化的状态信号**。该站每行首字符就是它自己的判定
  (红/黄/绿/白圆),直接读符号,不要用自然语言猜
- **通用原则**:凡是要写「判定」的地方,先问一句
  ——「这个结论是**站点告诉我的**,还是**我用正则猜的**?」优先用前者。
  猜出来的判定在跨版本、跨语言、跨措辞时会静默错,而且错得没有痕迹

## 坑-15 · Windows Git Bash 下「同一个目录」有两种字符串写法,比较必然失败

- **现象**:脚本里的守卫 `[ "$TOPLEVEL" = "$SRC_DIR" ]` 在 Windows 上**恒为假**遍历:
  - `pwd`(以及 `REPO_ROOT="$(cd … && pwd)"`)→ **POSIX 形**:`/f/projects/ouuut-browser`
  - `git rev-parse --show-toplevel` → **盘符形**:`F:/projects/ouuut-browser`
  - 两者指向**同一个目录**,但字符串永不相等
- **后果(实际踩到)**:**fail-closed 的守卫变成「永远拦下」** ——
  `tools/20-rebase.sh` 在非 dry-run 下永远在阶段 1 中止,而错误信息还说「chromium/src 没建好」。
  更糟的是:**危险情形(src 不是自己的工作树)与正确情形走同一条 die 分支**,守卫完全失去分辨能力。
  而 dry-run 分支只打印不比较,所以**冒烟测试抓不到**
- **正解**:任何路径比较前先归一化,且统一用 `pwd -P`:
  ```bash
  norm() { ( cd "$1" 2>/dev/null && pwd -P ); }   # 两边都过一遍再比
  [ "$(norm "$A")" = "$(norm "$B")" ] || die "..."
  ```
  另:先加一条与路径无关的直判更稳 —— `[ -d "$SRC_DIR/.git" ]` 就能拦住「git 会向上找到外层仓库」
  这个真正的危险
- **教训**:Windows 上的 shell 脚本,**「路径看起来一样」不等于「字符串一样」**。
  凡是拿路径做相等判断的地方,都要问一句「这两边是同一个编码体系吗」。

## 坑-16 · Windows PowerShell 5.1 把 UTF-8 无 BOM 的 `.ps1` 当 ANSI 读 → 整个脚本解析失败

- **现象**:`tools/00-bootstrap-toolchain.ps1` 用 Windows PowerShell 5.1 跑,
  直接吐一屏语法错误:
  ```
  表达式或语句中包含意外的标记“$What”。
  语句块或类型定义中缺少右“}”。
  ```
  报错里引用的源码片段是**乱码**(`throw "$What 澶辫触(exit ...)"`)。
  **而且外层 shell 看到的退出码是 0**(因为管道末端是 `tee`),不留意就会以为跑成功了
- **根因**:该文件是 **UTF-8 无 BOM**,里面写了中文。PowerShell 5.1 对**无 BOM 的 `.ps1`
  默认按 ANSI(本机 GBK)解码** → 中文字节被解成乱码 → 字符串字面量提前被某个乱码字节**
  终止 → 后面的中文变成裸 token → 语法树整个崩掉
- **为什么危险**:① 脚本**一行都没执行**(不是「跑了一半失败」),但退出码看着像成功;
  ② 报错文本本身是乱码,不看原文根本不知道是编码问题;
  ③ 这种失败**与脚本逻辑无关**,改逻辑多少次都没用
- **正解**:让 `.ps1` **纯 ASCII**(注释与提示语都写英文),把中文说明放到 `.md` 里。
  这比「加 BOM」更稳 —— 加 BOM 一旦被某个编辑器/工具重新保存为无 BOM 就会复发,
  而纯 ASCII 没有可失败的编码假设
- **验证手法**(值得固化成习惯):改完 `.ps1` 先只做**解析**检查,不要直接跑:
  ```bash
  powershell -NoProfile -Command "\$e=\$null; [void][System.Management.Automation.Language.Parser]::ParseFile('X.ps1',[ref]\$null,[ref]\$e); if(\$e.Count){\$e[0].Message}else{'PARSE OK'}"
  python -c "d=open('X.ps1','rb').read(); print('非 ASCII 字节:', sum(1 for b in d if b>127))"
  ```
- **附带**:`ps1 | tee log` 会吞掉真实退出码 —— 要判成败就用 `${PIPESTATUS[0]}` 或先重定向到文件再单独读 `$?`

## 坑-17 · `/f/...` 只被 bash 内建认,原生 Windows 程序会当成 C 盘路径

- **现象**:`git clone <url> /f/depot_tools` 报 `Cloning into '/f/depot_tools'...` 且 rc=0,
  但 `/f/depot_tools` 与 `F:/depot_tools` **都看不到内容**。实际落点是 **`C:\f\depot_tools`**
- **根因**:**本机的 bash 有两套路径写法,归属还不一致**
  - `bash` 内建(`[ -d ]`、`ls`、`cd`)认 POSIX 形 `/f/...`
  - 而**原生 Windows 程序**(`git.exe` 等)把 `/f/...` 当成「当前盘根下的 `f\...`」
    → cwd 在 C: 上时就成了 `C:\f\...`
  - 更麻烦的是**两个 shell 的 `pwd` 还不一样**:隐式 shell 给 `F:\projects\x`(反斜杠),
    显式 `"C:/Program Files/Git/bin/bash.exe"` 给 `/f/projects/x`
- **为什么危险**:命令**返回 0**、目标看起来「创建成功」,但东西落在完全不相干的位置。
  排查成本极高(本项目为此花了数轮)
- **正解**:
  1. **交给原生工具(git / gn / autoninja / gclient / cl.exe)的路径一律先归一化成 Windows 形**:
     ```bash
     winpath() { command -v cygpath >/dev/null 2>&1 && cygpath -w "$1" || printf '%s' "$1"; }
     REPO_ROOT="$(winpath "$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)")"
     ```
  2. **PATH 里加 depot_tools 时给 POSIX 形**(`/f/depot_tools`)—— 因为 `command -v` 是 bash 内建;
     给 Windows 形会让 `command -v gclient` **找不到**(实测)
  3. 脚本**调用同类工具时一律走显式 Git Bash 全路径**(坑-1 是间歇性的)

## 坑-18 · depot_tools 的工具名在 Windows 上有两套,`command -v` 会挑错

- **现象**:`export PATH="F:/depot_tools:$PATH"` 之后 `command -v gclient` **失败**,
  但目录里明明有 `gclient`、`gclient.bat`、`gclient.py` 三个
- **根因**:① PATH 用了 Windows 形(见坑-17-2);② Windows 上 depot_tools 把每个工具
  同时提供为「无扩展名脚本」与「`.bat` 包装」,而 **`.bat` 才会自己摆好 python 环境**
- **正解**:写一个解析器,按平台优先挑 `.bat`,并回退:
  ```bash
  IS_WINDOWS=0
  case "$(uname -s)" in *MINGW*|*MSYS*|*CYGWIN*|Windows_NT) IS_WINDOWS=1 ;; esac
  resolve_tool() {
    local cands c
    if [ "$IS_WINDOWS" -eq 1 ]; then cands="$1.bat $1"; else cands="$1 $1.bat"; fi
    for c in $cands; do command -v "$c" >/dev/null 2>&1 && { printf '%s' "$c"; return 0; }; done
    return 1
  }
  GCLIENT="$(resolve_tool gclient)"   # → gclient.bat
  ```
  另外 **`gn` / `autoninja` / `ninja` 在 depot_tools 第一次跑之前不存在** ——
  它们由 `gclient` 自己 bootstrap 出来,所以 sync 之后要**再解析一次**
- **附带**:Chromium 构建必须设 `DEPOT_TOOLS_WIN_TOOLCHAIN=0`,否则 depot_tools 会去抓
  Google 内部的 hermetic toolchain(非 Googler 抓不到)

## 坑-20 · `chromium.googlesource.com` 按 IP 限流(429),批量克隆必踩

- **现象**:`gclient sync` 拉到一半挂掉,报
  ```
  fatal: unable to access 'https://chromium.googlesource.com/external/github.com/google/pthreadpool.git/':
      The requested URL returned error: 429
  remote: RESOURCE_EXHAUSTED: Resource has been exhausted (e.g. check quota)
  remote:   subject: "shared/shared_anonymous"
  remote:   description: "Short term server-time rate limit exceeded"
  ```
  同时前面还有一堆 `WARNING: subprocess ... failed; will retry after a short nap...`
- **误判陷阱(重要)**:单看现象很容易以为「网络慢/不通」。我最初就是这么判的 ——
  实测 `git clone` 那个大仓库 **75 秒零字节增长**(TCP 已建立、CPU 近乎 0),
  于是去测速、换源。**其实根因是限流**,不是带宽。
  - 判别方法:同一时刻跑一个**小请求**(`git ls-remote --heads <url>`)——
    若它秒回,就说明「不是不通,是批量请求被限」
- **正解(三条一起上)**:
  1. **把 GitHub 出身的依赖改走 GitHub** —— `external/github.com/<org>/<repo>` 这类
     路径本来就是从 GitHub 镜像过去的,重写回去既快也不吃 Google 配额:
     ```bash
     git config --global --add url."https://github.com/".insteadOf \
         "https://chromium.googlesource.com/external/github.com/"
     git config --global --add url."https://github.com/webmproject/".insteadOf \
         "https://chromium.googlesource.com/webm/"
     git config --global --add url."https://github.com/".insteadOf \
         "https://chromium.googlesource.com/v8/"
     ```
     注意 `insteadOf` 用**最长前缀匹配**,所以针对性规则是安全的;
     **别**写一条 `.../ -> github.com/` 的泛规则(会把 `chromium/src.git` 也改坏)
  2. **外层包重试**:`gclient` 自己重试几轮后会放弃;`gclient sync` **幂等**,
     所以外层退避重跑是安全且有效的
  3. **必要时换出口 IP** —— 限流是按 IP 的
- **附带发现**:`chromium.googlesource.com` 上的大仓库克隆在本机基本不可用,
  **`github.com/chromium/chromium` 镜像**实测 25 秒下 179 MB(≈7.2 MB/s)。
  所以薄脚本里源码来源默认用 GitHub 镜像(见 `tools/10-fetch-chromium.sh` 的 `SRC_URL`)
- **⚠️ 镜像重写有一个副作用,必须知道**:`external/github.com/<org>/<repo>` **不一定**是
  1:1 的 GitHub 仓库 —— 有的指向**子目录**。实测踩到:
  ```
  chromium.googlesource.com/external/github.com/SeleniumHQ/selenium/py.git
      → 重写成 https://github.com/SeleniumHQ/selenium/py.git → not found
  ```
  而 `gclient` 会因为这个 dep 失败而**整个 sync 报错退出**。
  **修法**:在 `.gclient` 的 `custom_deps` 里把它设成 `None` 跳过
  (构建 Chrome 不需要 WebDriver 的 python 绑定)。
  **通用教训**:做**批量 URL 重写**时,一定要先确认「重写后的目标集合 ⊇ 重写前用到的所有路径」;
  CLI 或本机跑一次 **`tools/preflight-deps-mirror.py`** —— 它解析 `src/DEPS`,
  对每个 googlesource 依赖算出重写后的 URL 并 `git ls-remote` 探活,
  **直接输出可粘进 `.gclient` 的跳过块**。实测一次抓出 **10 个**不可达依赖,
  其中 **7 个是 LLVM monorepo 的子目录**
  (`libc++` / `libc++abi` / `libunwind` / `compiler-rt` / `llvm-libc` / `libFuzzer` / `clang-format`),
  另 3 个是 `v8/fuzzer_wasm_corpus`、`google/cld_3`、`SeleniumHQ/selenium/py`。
  **一个个追会追到天亮 —— 这一类问题要用工具一次解决,而且要能重复跑**
  (每换一个 Chromium 版本都要重跑:`10-fetch-chromium.sh` 已自动接线)
- **通用教训**:**当同一个错误第二次出现时,不要再修那一个实例,去修那个类。**
  我在这里追了三个实例(v8 规则、Selenium、llvm clang-format)才想到该写预检工具;
  写完一次就拿到了全部 10 个。
- **效果**:加上重写之后,**429 出现 0 次**,sync 一路推进到 100 万文件 / 19 GB
- **⚠️ 重写规则的三个陷阱(全是实测踩出来的)**:
  1. **别映射到没有 org 的前缀**。`:…/v8/` 直接映射到 `github.com/` 会得到
     `github.com/v8.git`(**不存在**);正确写法是映射到 `github.com/v8/`
     → `…/v8/v8.git`。**规则改完要按实际路径手推一遍**。
  2. **`external/github.com/<org>/<repo>` 不一定是 1:1 仓库**(可能指向子目录),
     这类要靠 `.gclient` 的 `custom_deps` 设 `None` 跳过。实测踩到两个:
     `SeleniumHQ/selenium/**py**`、`llvm/llvm-project/**clang/tools/clang-format**`。
     **一个 dep 失败会让整个 `gclient sync` 退出** —— 所以跳过名单必须齐全
  3. **别用 `git config --global` 写这些规则,用 `GIT_CONFIG_COUNT/KEY_n/VALUE_n` 环境变量**:
     - 只对本次进程及其子进程生效,**不污染用户的全局 gitconfig**
     - **不会留下旧规则** —— 写成 `--global` 之后,规则改一版就残留一版
       (实测:那条错的 v8 规则留在全局配置里,让我多排查了一轮)
     - 作者/CI 拿到脚本就能复现,不需要先跑一遍「配置命令」
     ```bash
     export GIT_CONFIG_COUNT=3
     export GIT_CONFIG_KEY_0="url.https://github.com/.insteadOf"
     export GIT_CONFIG_VALUE_0="https://chromium.googlesource.com/external/github.com/"
     ...
     ```
- **附带**:gclient 在「克隆失败 → 把冲突目录移到 `_bad_scm/` → 再试」这条路径上,
  如果目录**已经被移走过**,第二次 move 会抛 `FileNotFoundError` 而**不是**继续重试。
  所以失败后重跑前,清掉 `chromium/_bad_scm` 与残留的 `src/_gclient_*` 更省事
