### 1.2 从第 1 轮能得出的结论

1. **「按住 `Runtime.enable`」确实修好了它自己那一项**(🔴 → 🟢),并且顺带修好了
   `navigator.webdriver` 与 `ipcFloodingProtection`(两者是同一批启动参数的产物)。
2. **但远远不够** —— 仍然剩 **3 红 + 2 黄**,而且剩下的全部**不是 CDP 协议层的问题**:
   - `headless`:Playwright 无头 = `chrome-headless-shell`,UA 里直接写 `HeadlessChrome`,
     且 **`window.chrome` 压根没有** —— 这是**内核/无头模式层面**的结构性问题
   - `useragent`:内核是 Chromium 而非 Google Chrome
   - `storagePartitioning`:启动参数关掉了第三方存储分区
   - `viewport`:Playwright 默认 1280×720
3. **检测方已经知道 patchright** —— `storagePartitioning` 那一项的原文直接写
   「Playwright turns it off by default … and so do tools built on it, **including Patchright**」。
   也就是说「换一个已公开的补丁包」这条路,**对手已经把它当成一个已知签名**。

### 1.3 方向性含义(待第 2 轮定量)

**CDP 协议层不是唯一瓶颈,更不是最大瓶颈。** 真正的差距在**内核与启动参数**:

- 启动参数层:可修,且成本低(`--disable-features` 那一串、viewport、无头模式)
- 内核层:`HeadlessChrome` 标识 / 缺 `window.chrome` / Chromium-vs-Chrome —— **只能靠内核补丁**
  → 这**印证**了 `方案-v3-终稿.md` §五「C++ 源码级补丁是唯一站得住的隐身层」

因此**不能**据此直接宣布 F17 可取消 —— 需要第 2 轮把 `pw-hardened`
(只修启动参数、不修协议)加进来,三格连起来才能分离两个变量的贡献。
