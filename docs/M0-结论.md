## 二、结论

### 2.1 两个变量**正交**,各自只解决自己那一半

这是本轮最硬的发现:

| | 修了什么 | 没修什么 |
|---|---|---|
| **`patchright`(只修协议层)** | `runtimeEnableLeak`、`navigatorWebdriver`、`ipcFloodingProtection` | `useragent`、`headless`、`storagePartitioning`、`viewport`、`popupBlocking` |
| **`pw-hardened`(只修启动参数)** | `storagePartitioning`、`viewport`、`popupBlocking`、`navigatorWebdriver` | **`runtimeEnableLeak`(又回来了)**、`useragent`、`headless` |

**两者的红项集合有重合,但各自的「独有红项」互不重叠** ——
`patchright` 独有 `storagePartitioning`,`pw-hardened` 独有 `runtimeEnableLeak`
(重合的是 `useragent` / `headless`,那两项两者都修不了)。这正是「两个变量正交」的直接证据:

> **「按住 `Runtime.enable`」修不掉启动参数的问题;「修启动参数」也修不掉协议层的问题。**

反过来也说明:**协议层确实有独立贡献**(`pw-hardened` 参数全干净,`runtimeEnableLeak` 照样红)。
所以**不能**因为 patchright 修好了它,就宣布 F17 可取消。

### 2.2 剩下的红项只能靠**内核层** —— 而 `ego` 证明了内核层能做到**全绿**

**最重要的单条实测(第 4 轮,`probe/out/20261024-021513`)**:`ego` 在 bot-detector 上
**16 项全绿、0 红 0 黄** —— 是全场唯一全绿的 target。

| 项 | ego 的表现(站点原文) |
|---|---|
| `useragent` | 🟢 `brands` 含 **`Google Chrome`**:`[{Chromium,154.0.8037.44},{Google Chrome,154.0.8037.44}]` |
| `headless` | 🟢 **"No signs of headless Chrome"**;UA = `Chrome/154.0.0.0`(**无 `HeadlessChrome`**);`windowChrome: "object"`;`notificationPermission: "default"` |
| `runtimeEnableLeak` | 🟢 |
| `storagePartitioning` / `viewport` / `popupBlocking` / `ipcFloodingProtection` | 🟢 全绿 |

**这条证据的价值:**

1. **全绿是可达的**,而且用的是 Chromium —— 不是「反检测不可能」的空论
2. **它恰好由我们识别出的三层组成**:驱动层(不发 `Runtime.enable`)+ 启动参数白名单
   + **内核层品牌/无头补丁** → 三层的**具体形态被 ego 演示了一遍**
3. **它给本项目定了真实标杆**:目标不是「超过 CloakBrowser」,而是 **「达到 ego 的 16/16,
   同时补上 ego 缺的档案隔离 / 服务器化 / 开源可审计」**
4. 与 REA 结论一致:ego 的主通道是 Mojo/ipcz 私有 IPC,B1/B2 的推断在**运行时被证实**

**⚠️ 对 ADR-006 的细化(必须记住)**:ego 的做法是 —— **版本号保持真实**
(`154.0.8037.44` = 内核真版本),但**品牌伪装成 `Google Chrome`**。
也就是说:

> **「绝不伪造 UA 版本」与「必须伪装成 Google Chrome 品牌」是两件事。**
> 版本必须真(否则特性检测对不上);品牌必须像 Chrome(因为检测方的基线就是 Chrome)。

因此 `pw-naive` / `patchright` / `pw-hardened` 三者都红的 `useragent` / `headless` 两项,
**归 M1 的内核补丁**,且**已有现成参考形态**(可测、可复现)。

> **这印证了 `方案-v3-终稿.md` §五的判断:「C++ 源码级补丁是唯一站得住的隐身层」。**
> 也就是说,**M1(内核构建)才是主战场**,而不是 F17。

### 2.3 对 F17 的判定(**已确认**)

**问题**:「按住 `Runtime.enable` 是否已足够过检测」→ **不够。**

**证据**:`patchright`(按住 `Runtime.enable`)之后仍有 **3 红**(`useragent` / `headless` /
`storagePartitioning`);`pw-hardened`(参数全干净)**`runtimeEnableLeak` 照样红** →
说明协议层有独立贡献,两者都**必要**。

**但 F17 的范围要大幅收窄 —— 不需要自研 IPC 协议栈:**

| 原假设(F17) | 实测修正 |
|---|---|
| 自研进程内 IPC 协议栈,4–6 周 | **驱动层按住副作用命令(约几百行)+ 启动参数白名单(约 10 行)**,**1 周以内** |

`patchright-hardened` 证明:红项从 **6 → 2**,而它**一行内核代码都没有**。
剩下两项红(`useragent` / `headless`)是**内核品牌与无头标识**,归 M1 —— 那本来就
是我们的主战场,不是额外成本。

**因此建议**:
1. **F17 从「自研协议栈」降级为「驱动层补丁 + 参数白名单」**,工期 4–6 周 → **≤1 周**
2. 省下的时间**全部投给 M1(内核构建)**,因为剩余红项只有内核能修
3. **不要直接用 patchright**:检测方已点名它(§2.4)。要**抄做法、自己实现**

**确立的修复责任分工(可直接当 M4 的需求书)**:

| 红/黄项 | 归属层 | 具体做法 | 成本 |
|---|---|---|---|
| `runtimeEnableLeak` | **驱动层** | 不发 `Runtime.enable`;改 `addBinding` 方式解析 context id(自实现) | 数天 |
| `navigatorWebdriver` | 启动参数 | `--disable-blink-features=AutomationControlled` | 1 行 |
| `ipcFloodingProtection` | 启动参数 | **去掉** `--disable-ipc-flooding-protection` | 1 行 |
| `popupBlocking` | 启动参数 | **去掉** `--disable-popup-blocking` | 1 行 |
| `storagePartitioning` | 启动参数 | 自己的 `--disable-features=` 不含 `ThirdPartyStoragePartitioning` | 1 行 |
| `viewport` | 会话参数 | 视口按真实屏幕,不用 1280×720 默认值 | 1 行 |
| `useragent` | **内核层** | `userAgentData.brands` 里要有 `Google Chrome` | M1 |
| `headless` | **内核层** | UA 去掉 `HeadlessChrome`;补 `window.chrome`;WebGL 不用 SwiftShader | M1 |

### 2.4 第二条独立发现:**「换成已公开的补丁包」已经是一个已知签名**

`storagePartitioning` 那一项的报错原文直接写:

> "Playwright turns it off by default (--disable-features=...ThirdPartyStoragePartitioning...),
> and so do tools built on it, **including Patchright**. Use rebrowser-patches to fix it."

**检测方知道 patchright 的存在并点名它。** 含义:

- 我们**不能**只是「用 patchright」—— 那样等于用一个有名字的签名
- 但我们可以**抄它的做法**(按住那些命令),自己实现,并同时把启动参数修干净
- 这正是 M2「自写原生层」的价值所在

### 4.1 Turnstile:先说踩到的坑,再说结论

**坑**:第一版用的是 Cloudflare **官方** dummy demo(`demo.turnstile.workers.dev`)。
它 200、控件正常渲染、还真发 token,`pw-naive` 与 `ego` 都 `passed` —— 看起来是完美证据。
**但 token 的值是 `XXXX.DUMMY.TOKEN`**:该站用 **dummy sitekey**,对任何客户端都直接发假 token、
**不做任何评分**。那一轮**什么都不证明**。

现在探针会识别这个假 token 并把结果判 `error`(而不是 `passed`),同时在 `detail.calibration`
里明说「本次无判别力」。

**换到真 sitekey 的演示站之后**(`2captcha.com/demo/cloudflare-turnstile`):

| target | 结果 | 证据 |
|---|---|---|
| `pw-naive` | **detected** | 控件渲染了(1 个),等了 25.5s,**token 始终为空** |
| `ego` | **detected** | 同上 |

即:**在真 Cloudflare 面前,两个 target 都拿不到免交互 token,都被要求人工交互。**
—— 而本探针**从不点击**(见 `probe/sites/turnstile.py` 头部:L3 红线,不做自动过验证码)。

**这条结论的限定**:`2captcha.com` 本身是打码服务商的演示页,它可能**故意**把控件配成
总是要求交互(好演示「我们能解」)。因此这条结果**有判别力但不中立**;
需要第二家真 sitekey 的站才能定论。备选 `peet.ws/turnstile-test/` 实测**控件选不中**
(探针 `error`),`nopecha.com/demo/cloudflare` 与 `turnstile.zeroclover.io` **直连 403**。

**另外**:`ego` 在这两个 Turnstile 站上的用时明显更长(29s → 59s 级),
与「它要等 Cloudflare 的判定」一致,但这只是用时,不足以当结论。

**结论的适用边界**:本文 §二 的判定建立在 `bot-detector.rebrowser.net`(16 项逐测)
+ `browserleaks`(WebRTC)+ `creepjs`(headless 轴)+ Turnstile(真 sitekey)上,
出口覆盖**本机直连**与**机房节点**两种。
**尚未**在一个**中立的、用真 sitekey 的** Turnstile 站上验证。

## 五、方法学教训(已回填 `docs/坑与解法.md`)

| 教训 | 坑号 |

| Playwright `ignore_default_args=True` 会让浏览器起不来 | 坑-10 |
| `ego-browser` 脚本的 `console.log` 走 stderr | 坑-11 |
